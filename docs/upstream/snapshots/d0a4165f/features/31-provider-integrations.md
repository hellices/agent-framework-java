## Purpose and boundary

This document produces a complete **catalog of the packaged integration surface** of the pinned upstream. Features whose detailed designs have already been written are cross-referenced rather than re-explained; the focus here is strictly on inventory: **what exists as a package / what maturity level / which core port it plugs into / whether a README and tests are present / what to port first in a Java adapter**.  
Detailed wire contracts are deferred to existing documents: Code Execution·Skills·Background in [13](./13-skills-background-code.md), general Hosting in [20](./20-hosting.md), OpenAI Responses hosting in [21](./21-openai-responses-hosting.md), A2A in [22](./22-a2a.md), AG-UI in [23](./23-ag-ui.md), MCP hosting in [24](./24-mcp-hosting.md), Foundry/DevUI/channels in [25](./25-foundry-devui-channels.md), identity/session routing in [26](./26-identity-session-routing.md).  
The upstream itself claims to be a production-grade agent/workflow framework in both `.NET` and `Python`. ([root README](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/README.md#L12-L18))

## Inventory method

1. All 33 `dotnet/src/**/*.csproj` files and all 35 `python/packages/*/pyproject.toml` files were enumerated in full.
2. For `.NET`, it was confirmed that the central package metadata is computed from the `VersionPrefix=1.17.0` and `IsReleased`/`VersionSuffix` rules in `dotnet/nuget/nuget-package.props`. ([nuget-package.props](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/nuget/nuget-package.props#L4-L10))
3. The `ProjectReference` entries in `dotnet/tests/**/*.csproj` were traced to confirm that each source project is referenced by at least one test project.
4. For `Python`, the `name`/`version`/`readme`/`requires-python` fields of each `pyproject.toml` were cross-checked against the released/beta/alpha designations in `PACKAGE_STATUS.md`. ([Python package status table](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/PACKAGE_STATUS.md#L13-L52))
5. For each package/project, candidate public entry points (`public class`/`public static class`, Python `__init__.py` exports, `project.scripts`) and the presence of a README were verified.
6. Finally, a self-set cross-check confirmed that every `dotnet/src/...csproj` and `python/packages/.../pyproject.toml` path string appears in the body of this document.

2. Many `.NET` packages lack a package-local README, but the actual package metadata uses the central `dotnet/nuget/NUGET.md` as an automatic README. Accordingly, this should be understood as “central README fallback” rather than “no README”. ## Java adapter priority and module decisions

### Priority

1. **P0 core parity**: `Microsoft.Agents.AI` / `agent-framework-core`, workflows, declarative, session/history abstractions.
2. **P1 shared providers**: OpenAI, Foundry, GitHub Copilot, A2A client/hosting, AG-UI, generic hosting.
3. **P2 persistence/governance**: Cosmos history/checkpoint, Redis/Valkey, Mem0, Purview.
4. **P3 managed/runtime adapters**: Foundry Hosting, DevUI, MCP hosting seam.
5. **P4 language- or runtime-specific extras**: LocalCodeAct, Hyperlight, Monty, Azure AI Persistent Agents, ChatKit, Telegram, Bedrock/Gemini/Mistral/Ollama.

### Recommended modules

- `agent-framework-java-core`
- `agent-framework-java-session`
- `agent-framework-java-workflows`
- `agent-framework-java-declarative`
- `agent-framework-java-provider-openai`

- `agent-framework-java-storage-cosmos`

- `agent-framework-java-security-purview`

### Module decision principles

- `ChatClient`-type providers are split into **per-provider modules**.
- Persistence separates `history/checkpoint` from `semantic memory`.
- Protocol hosting separates `generic hosting core` from `wire adapter`.
- Code execution is not embedded directly in the Java core; it is placed in an `SPI + optional runtime module`.
- Python-only or .NET-only providers are placed in an optional adapter tier, not as first-class core dependencies.

## Minimum acceptance scenarios

1. A Java core agent plugs in the OpenAI provider and performs text + tool call + embedding.
2. A Java workflow runs multi-agent orchestration with the Foundry provider.
3. A Java host exposes an OpenAI Responses-compatible endpoint and preserves `previous_response_id` continuity.
4. A Java host calls a remote agent via an A2A client and also exposes a local agent as an A2A server.
5. A Java host streams an AG-UI stream via SSE and maps approval interrupts to UI events.
6. A Java runtime uses a Cosmos- or Redis-backed history/checkpoint store to perform resume.
7. A Java runtime connects the Mem0 context provider to perform long-term memory recall.
8. A Java middleware chain inserts Purview policy to perform outbound/inbound policy evaluation.
9. A Java declarative loader resolves provider aliases to create an agent/workflow.
10. A Java MCP hosting adapter exposes a local tool/workflow as an MCP tool.
11. The Java code execution SPI can plug in a Hyperlight-class sandbox or an alternative runtime.
12. A Java DevUI/diagnostic host visualizes run/update/trace/session snapshots.
