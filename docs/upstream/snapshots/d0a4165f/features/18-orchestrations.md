## Purpose and boundary

### Purpose

- The purpose of the orchestration layer is to encapsulate frequently used collaboration patterns as a dedicated builder surface, rather than connecting individual executors/agents directly. This layer provides the participant list, coordination rules, terminal/intermediate output contract, optional HITL wrapper, and checkpoint-enabled runtime wiring all at once. ([.NET Sequential remarks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L10-L23), [.NET Concurrent remarks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/ConcurrentWorkflowBuilder.cs#L13-L27), [Python Sequential builder overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L65-L96), [Python GroupChat builder overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py#L593-L613))

### Boundary

- The included scope is as follows.
  - orchestration builder API
  - participant resolution and wrapper selection
  - orchestration-specific graph lowering
  - orchestration-specific state and checkpoint hooks
  - orchestration-specific output designation/HITL defaults
- The excluded scope is as follows.
  - core workflow graph validation details
  - generic workflow runtime loop
  - declarative YAML workflows
  - generic workflow-as-agent composition internals  
  This separation is also evident in the fact that in .NET, the implementation is split across `OrchestrationBuilderBase` and each orchestration builder file, and in Python, across `_participant_output_config.py`, `_workflow_builder.py`, and each orchestration builder file. ([.NET OrchestrationBuilderBase](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/OrchestrationBuilderBase.cs#L16-L153), [Python OrchestrationWorkflowBuilder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_workflow_builder.py#L1-L12), [Python participant output config](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_participant_output_config.py#L63-L168))

## Public APIs and types

### Common .NET surface

- The helper entrypoint is `AgentWorkflowBuilder`. It provides creation of sequential/concurrent/handoff/group-chat/magentic builders, or immediate build helpers. ### Common Python surface

- The orchestration runtime uses `OrchestrationWorkflowBuilder`, which directly subclasses the core `WorkflowBuilder`. This subclass only redirects feature usage attribution to the orchestration side; the actual graph build behavior uses the core builder as-is. ([OrchestrationWorkflowBuilder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_workflow_builder.py#L1-L12))
- The common participant output contract is handled by `_resolve_participant_output_config(...)`. This helper applies `output_from`, `intermediate_output_from`, `all`, `all_other`, explicit defaults suppression, and overlap rejection identically across all orchestrations. ([participant output config resolution](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_participant_output_config.py#L63-L136))

This wrapper creates an inner workflow that encapsulates the agent response approval/enrichment flow within the orchestration boundary. ([AgentApprovalExecutor overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_orchestration_request_info.py#L169-L236))

## Sub-feature 1. Sequential Orchestration

### Purpose and boundary

- Sequential orchestration is a pipeline that executes participants in order. .NET builds a pipeline where “the output of one agent is the input of the next” and attaches an aggregator at the end, while Python normalizes the input to a `list[Message]` conversation and then builds the participant chain. ([.NET Sequential overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L10-L23), [Python Sequential overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L65-L96))

### Public APIs and types

- .NET provides `SequentialWorkflowBuilder(params IEnumerable<AIAgent> agents)` and `WithChainOnlyAgentResponses(bool)`. The helper entrypoints are `AgentWorkflowBuilder.BuildSequential(...)` / `CreateSequentialBuilderWith(...)`. ([Sequential builder ctor/options](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L23-L58), [AgentWorkflowBuilder sequential helpers](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/AgentWorkflowBuilder.cs#L15-L74), [CreateSequentialBuilderWith](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/AgentWorkflowBuilder.cs#L162-L169))
- Python provides `SequentialBuilder(participants=..., checkpoint_storage=..., chain_only_agent_responses=..., output_from=..., intermediate_output_from=...)` and `with_request_info(...)`. ([Python SequentialBuilder ctor](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L98-L129), [with_request_info](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L156-L187))

### Detailed execution flow

- .NET configures `AIAgentHostOptions`, converts all agents to executor bindings, and connects the bindings with serial edges. At the end, it appends an `OutputMessagesExecutor` to make the accumulated `ChatMessage`s the final workflow output; the default designation is end terminal plus all agents intermediate. ([Sequential build flow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L68-L101))
- With `WithChainOnlyAgentResponses(true)`, `ForwardIncomingMessages=false` is set, causing downstream agents to receive only the immediately preceding agent's response instead of the full accumulated conversation. Tests pin this difference. ([chain_only_agent_responses option](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L42-L58), [default full conversation test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/SequentialWorkflowBuilderTests.cs#L74-L90), [chain-only test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/SequentialWorkflowBuilderTests.cs#L92-L108))
- Python has the `_InputToConversation` executor normalize string/message/list input to `list[Message]`, then connects participants in order. When `chain_only_agent_responses=True`, the wrapped `AgentExecutor`'s `context_mode` changes to `last_agent`. ([input normalizer](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L49-L63), [resolve participants / context_mode](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L201-L229), [build graph](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L231-L272))

### State and persistence

- The .NET sequential builder itself does not create any separate orchestration state. Persisted state belongs to each participant executor's session/state and to the terminal output executor's flow. The builder only adds name/description/output designation. ([Sequential build structure](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L83-L101))
- Python likewise has no orchestration-specific state object. However, when `with_request_info()` is used, participants are wrapped in an `AgentApprovalExecutor` inner workflow, creating a subworkflow checkpoint/state for approval resumption within the participant boundary. ([Sequential with_request_info wrapper selection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L213-L225), [AgentApprovalExecutor inner workflow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_orchestration_request_info.py#L206-L236))

### Extension points

- .NET extension points are participant ordering, metadata, output designation, and chain-only mode. The orchestration-specific builder surface is relatively thin. ([Sequential builder options](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L23-L58))

([Sequential with_request_info](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L156-L187))

### Concurrency, streaming, and cancellation

- Sequential orchestration has no parallelism between participants. Streaming depends on the updates emitted by the participant wrapper, and the chain-only/full-conversation difference affects only input shaping. ([Sequential tests run order](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/SequentialWorkflowBuilderTests.cs#L34-L72))

## Sub-feature 2. Concurrent Orchestration

### Purpose and boundary

- Concurrent orchestration is a pattern that fans out the same input to multiple participants and combines them with a fan-in aggregator. ([.NET Concurrent overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/ConcurrentWorkflowBuilder.cs#L13-L27), [Python Concurrent overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_concurrent.py#L34-L52))

### Public APIs and types

### Detailed execution flow

- The .NET handoff build creates `HandoffStartExecutor` and `HandoffEndExecutor`, and generates a `HandoffAgentExecutor` factory binding for each participant. If no explicit handoffs are provided, default mesh handoffs are created. When `EnableReturnToPrevious()` is on, the start executor downstream becomes a switch; when autonomous mode is on, a self-loop routing switch is added downstream of the end executor. ([create executor bindings and default mesh](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/HandoffWorkflowBuilder.cs#L445-L544), [build graph and switches](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/HandoffWorkflowBuilder.cs#L546-L638))
- The .NET runtime center is `HandoffAgentExecutor`. If the incoming state contains a handoff target, it filters out the source agent's handoff function call/tool result messages and forwards the remainder to the target agent; if there is no handoff and termination is false, it proceeds to `HandoffEndExecutor` or the autonomous loop-back. Handoff is not permitted while there are pending approval/function-call requests. ([message filtering and invocation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/HandoffAgentExecutor.cs#L241-L260), [shared conversation/autonomous/termination path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/HandoffAgentExecutor.cs#L262-L345), [agent streaming updates and handoff detection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/HandoffAgentExecutor.cs#L425-L509))
- Python handoff builds a fully connected participant graph, and the actual handoff mechanics are handled by each `HandoffAgentExecutor`'s internal tool/middleware/state. If no explicit handoff config is provided, a mesh topology is created in which all agents can hand off to one another. ([Python build graph fully connected](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_handoff.py#L931-L1011), [default mesh handoff config](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_handoff.py#L1026-L1073), [executor resolution with autonomous flags](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_handoff.py#L1075-L1115))

### Detailed execution flow

- .NET's `GroupChatHost` is the actual orchestrator executor that holds the canonical conversation. ([GroupChatWorkflowBuilder build graph](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/GroupChatWorkflowBuilder.cs#L64-L90), [host broadcast excludes current speaker](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/GroupChatHost.cs#L96-L109))

([GroupChatBuilder build graph](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py#L1005-L1040), [selection-function orchestrator flow hits](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py#L929-L964))

## Sub-feature 5. Magentic Orchestration

### Purpose and boundary

- Magentic orchestration is a planning-centric pattern in which the manager is responsible for task planning, a progress ledger, replanning, and final answer synthesis. It is an orchestration with stronger planning/replanning/HITL review than ordinary group-chat. ([.NET Magentic overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/MagenticWorkflowBuilder.cs#L16-L29), [Python Magentic overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py#L1381-L1400))

## .NET/Python differences

- The **default output contract** is the largest difference.  
  - Sequential: .NET is terminal end executor + agents intermediate, Python is last participant only as terminal

  - Handoff: .NET is end executor terminal + agents intermediate, Python is all participants as terminal

## Java decisions

- The Java orchestration layer must separate the **common participant-output designation helper** from the **pattern-specific builders**. Because Python's `_participant_output_config.py` and .NET's `OrchestrationBuilderBase` each solve the same problem in different ways, pulling this out into an explicit shared module in Java is preferable for maintainability. ([.NET OrchestrationBuilderBase](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/OrchestrationBuilderBase.cs#L49-L153), [Python participant output helper](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_participant_output_config.py#L63-L136))
- Java should not leave output defaults as implicit per-language conventions; it is better to define `defaultOutputPolicy` explicitly as an internal constant or public enum for each orchestration builder. Directly inheriting the current .NET/Python drift would break cross-language parity. ([.NET vs Python default contracts across builders](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SequentialWorkflowBuilder.cs#L94-L99), [Python Sequential defaults](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L252-L265), [Python Handoff docs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_handoff.py#L582-L592))
- Java handoff should, like Python, place validation that enforces provider capabilities (`must be Agent`, `require_per_service_call_history_persistence`) at build time. This reduces user confusion and runtime corruption. ([Python handoff validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_handoff.py#L697-L702), [service-call-history persistence requirement](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_handoff.py#L951-L968))
- Java Magentic must abstract plan review, progress ledger, and replanning into a single “manager SPI.” Referencing Python's four paths (`manager / manager_factory / manager_agent / manager_agent_factory`) and .NET's manager-agent-based orchestrator, the public builder should have an exactly-one manager source contract. ([Python exactly-one manager source](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py#L1658-L1664), [.NET manager-agent binding](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/MagenticWorkflowBuilder.cs#L212-L220))
- Java sequential/concurrent/group-chat should include a Python-style `withRequestInfo(...)` wrapper surface. Having a generic HITL wrapper on the builder surface makes the orchestration user experience consistent and makes it easy to distinguish from the specialized flows (handoff/magentic). ([Python request_info wrapper surfaces](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_sequential.py#L156-L187), [Concurrent request_info](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_concurrent.py#L326-L357), [GroupChat request_info](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_group_chat.py#L884-L911))
