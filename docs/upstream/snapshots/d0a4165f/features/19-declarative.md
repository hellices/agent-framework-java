## Purpose and boundary

### Purpose

- The purpose of the declarative layer is to **define agents and workflows using YAML/asset schemas rather than code** and to convert them into **an executable runtime graph and provider/tool/http/mcp integrations**.  
  - .NET focuses on declarative lowering of the workflow side and declarative action execution.
  - Python additionally includes YAML prompt-agent asset creation.  
  ([.NET declarative workflow builder purpose](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/DeclarativeWorkflowBuilder.cs#L14-L18), [Python WorkflowFactory purpose](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L43-L50), [Python AgentFactory purpose](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_loader.py#L143-L149))

### Boundary

- The included scope is as follows.
  - agent asset YAML form and schema normalization
  - declarative workflow definition shape
  - workflow graph lowering and root executor behavior
  - declarative state / PowerFx env / path safety
  - action executors (`InvokeAzureAgent`, `InvokeFunctionTool`, `InvokeMcpTool`, `HttpRequestAction`, `Question`, `RequestExternalInput`, `SendActivity`, control-flow lowering)
  - MCP integration package/handler
  - .NET source generation/JSON source generation and Python runtime-driven implementation differences
- The excluded scope is as follows.
  - the generic core workflow graph/runtime itself
  - orchestration builders
  - generic workflow-as-agent composition
  - host/web transport  
  Based on the inspected code, this document directly targets .NET `DeclarativeWorkflowBuilder`, `WorkflowActionVisitor`, `DeclarativeWorkflowExecutor`, `ObjectModel/*`, `DeclarativeWorkflowJsonOptions`, `DefaultHttpRequestHandler`, `DefaultMcpToolHandler` and Python `_loader.py`, `_models.py`, `_workflows/*`, declarative tests, and declarative asset samples. ([.NET workflow lowering surface](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/WorkflowActionVisitor.cs#L15-L64), [Python workflow builder surface](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L111-L129), [Python agent schema/model surface](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_models.py#L83-L140))

## Detailed execution flow

### Sub-feature 1. Declarative agent assets / schema

- The canonical YAML shape of a Python declarative agent asset is shown by the sample files. `OpenAI.yaml` uses `kind: Prompt`, `model.provider`, `model.apiType`, `connection`, and `outputSchema.properties`, while `GetWeather.yaml` declares a function tool and parameter schema/bindings under `tools`. ([OpenAI agent sample](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/declarative-agents/agent-samples/openai/OpenAI.yaml#L1-L29), [chatclient function-tool sample](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/declarative-agents/agent-samples/chatclient/GetWeather.yaml#L1-L30))
- Python `AgentFactory.create_agent_from_dict(...)` converts the YAML dict into a schema object via `agent_schema_dispatch(...)`, then enforces that the result must be a `PromptAgent`. It then creates a chat client and combines `tools` and `outputSchema` as `default_options` to produce an `Agent`. ([AgentFactory create_agent_from_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_loader.py#L418-L484))
- The Python asset loader can apply PowerFx expressions to YAML scalars. `_try_powerfx_eval(...)` evaluates values that start with `=`; when `safe_mode=True` it blocks the `Env` symbol, and only when `safe_mode=False` does it place `os.environ` in `Env`. Coupled with the README identifying this as the experimental declarative agent path, the Python asset loader is a surface where trust boundaries matter. ([safe_mode context and PowerFx eval](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_models.py#L37-L80), [AgentFactory safe_mode docs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_loader.py#L236-L245))
- Python `WorkflowFactory` can resolve agents from the `agents:` section in the workflow YAML by combining an inline dict, a `file:` reference, or a pre-registered agent registry. However, `connection`-based agent definitions currently require passing a pre-created agent via the `agents=` parameter and do not support inline auto-construction. ([create_workflow_from_definition agents section](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L374-L404), [_create_agent_from_def](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L549-L585))
- In the .NET inspected scope, only workflow YAML samples are officially documented. The workflow sample README describes only that a declarative workflow is a single YAML file and can be run locally via `DeclarativeWorkflowBuilder.Build(...)`. No YAML prompt-agent asset loader equivalent to Python's `AgentFactory` was confirmed in the inspected scope. ([workflow-samples README](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/declarative-agents/workflow-samples/README.md#L1-L17))

### Sub-feature 2. Declarative workflow graph / runtime / state

- The entry point for a .NET declarative workflow is `Build<TInput>(TextReader yamlReader, DeclarativeWorkflowOptions options, ...)`. The YAML root is read via `YamlSerializer.Deserialize<BotElement>`, the root must be `AdaptiveDialog`, and `"Workflow"` is an alias for `"AdaptiveDialog"`. ([.NET Build<TInput>](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/DeclarativeWorkflowBuilder.cs#L51-L88), [ReadWorkflow root check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/DeclarativeWorkflowBuilder.cs#L90-L101))
- .NET lowering is performed by `WorkflowActionVisitor`. This visitor decomposes action scopes, condition groups, goto, foreach, question, request external input, and more into graph nodes and edges, and finally creates a core `WorkflowBuilder` via `WorkflowModelBuilder`. If telemetry is enabled, OpenTelemetry configuration is also attached at build time. ([WorkflowActionVisitor complete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/WorkflowActionVisitor.cs#L35-L64), [scope/condition/loop lowering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/WorkflowActionVisitor.cs#L66-L208), [question/request-external-input lowering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/WorkflowActionVisitor.cs#L248-L296))
- The .NET root executor `DeclarativeWorkflowExecutor<TInput>` accepts `string`, `ChatMessage`, `IEnumerable<ChatMessage>`, `ChatMessage[]`, and `TurnToken` in addition to `TInput`, satisfying both chat protocol hosting and direct invocation simultaneously. An inbound `TurnToken` is a no-op in practice; only non-token input triggers graph advance. ([DeclarativeWorkflowExecutor input shapes](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/DeclarativeWorkflowExecutor.cs#L17-L33), [chat protocol route registration](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/DeclarativeWorkflowExecutor.cs#L57-L145))
- For a Python declarative workflow, `WorkflowFactory.create_workflow_from_definition(...)` determines the workflow name/description, creates and merges `agents:`, creates a `DeclarativeEnvConfig`, and then creates the graph via `DeclarativeWorkflowBuilder`. This builder accepts either a top-level `actions:` or `trigger.actions`. ([WorkflowFactory create_workflow_from_definition](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L321-L404), [workflow normalization](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L479-L547))
- Python `DeclarativeWorkflowBuilder` places a `_workflow_entry` join node as the start executor and creates action executors, evaluators, loop helper nodes, and goto back-edges to lower the graph into a core workflow graph. Empty workflows are rejected, and schema validation together with circular goto detection are also performed before the build. ([DeclarativeWorkflowBuilder init/build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L132-L239), [validation pre-pass](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L241-L334))
- Python declarative state has the `Inputs`, `Outputs`, `Local`, `System`, `Agent`, `Conversation`, `Custom`, and `_declarative_loop_state` namespaces. The `Env` symbol is controlled by `DeclarativeEnvConfig`, and safe path access distinguishes between dict-key and object-attribute. ([DeclarativeEnvConfig](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L70-L123), [DeclarativeStateData schema](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L175-L203), [DeclarativeWorkflowState namespaces/init](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L257-L321))
- Path safety is an important differentiator in the Python implementation. `get()` allows arbitrary strings for dict-keyed path segments but permits only `[A-Za-z][A-Za-z0-9_]*` for object-attribute path segments. `set()`/`append()` reject empty segments, and `Workflow.Inputs` is read-only. Tests pin that exfiltration chains such as `__class__.__globals__.os.environ` are blocked. ([safe path regex and get/set/append rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L64-L67), [get path enforcement](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L337-L405), [set/append validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L407-L497), [state path safety tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_state_path_safety.py#L7-L24), [exfil rejection tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_state_path_safety.py#L90-L133))
- Python declarative root state initialization has a composition-specific nuance: when `_ensure_state_initialized(...)` receives a list-of-`Message` input, it checks whether prior turn state exists and takes the continuation branch without calling `state.initialize()` again. This preserves prior declarative conversation/system/local state across `Workflow.as_agent()` multi-turn scenarios. ([continuation detection in _ensure_state_initialized](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L1077-L1160), [as_agent continuation regression test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_workflow_factory.py#L280-L339))

### Sub-feature 3. Agent / tool / HTTP / external-input action executors

- The .NET `InvokeAzureAgentExecutor` uses `conversationId`, structured `input.arguments`, `input.messages`, `input.externalLoop.when`, `output.responseObject`, `output.messages`, and `output.autoSend`. ## Concurrency, streaming, and cancellation

- The declarative workflow is built on top of the generic core runtime and therefore does not change the superstep concurrency/cancel policy itself. The declarative-specific difference is **where inside the action executor the workflow pauses and resumes**.
- When .NET `DeclarativeWorkflowExecutor<TInput>` receives `ChatMessage[]`/`IEnumerable<ChatMessage>`, it iterates through multiple messages but calls `SendResultMessageAsync(...)` with `finalizeTurn=true` only on the last message. `TurnToken` is a no-op, so a token sent by the host does not double-trigger root advance. ([multiple chat messages handling](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/DeclarativeWorkflowExecutor.cs#L113-L145), [AdvanceAsync finalizeTurn](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/DeclarativeWorkflowExecutor.cs#L147-L186))
- The external loop of Python `InvokeAzureAgentExecutor` alternates between user input and agent response while checking the loop condition. When the condition is true it pauses via request_info; when false it sends `ActionComplete` to advance the graph again. ([first loop yield](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_agents.py#L834-L871), [resume and re-evaluate loop condition](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_agents.py#L921-L1010))
- Python HTTP/MCP default handlers are concurrency-safe by contract.  
  - `HttpRequestHandler` protocol doc says implementations must be safe to call concurrently from multiple workflow runs.
  - `DefaultMCPToolHandler` uses async lock + inflight futures for cache/connect coordination.  
  ([HttpRequestHandler concurrency contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_http_handler.py#L90-L112), [DefaultMCPToolHandler cache/inflight coordination](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_mcp_handler.py#L220-L229))
- Regarding cancellation, the Python HTTP action does not catch `asyncio.CancelledError` and lets it propagate. The .NET HTTP action also distinguishes between timeout and caller cancellation. ## Errors, validation, and security

- Python `WorkflowFactory._validate_workflow_def(...)` checks whether the workflow definition is a dict, whether actions is a list, whether each action is a dict, whether `kind` is present, and whether top-level `actions` or `trigger.actions` is present. ([workflow_def validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L494-L520))
- The Python declarative builder validates action-required fields and unsupported `ConditionGroup` fields in a schema pre-pass and rejects empty workflows. ([DeclarativeWorkflowBuilder required fields map](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L63-L108), [empty workflow / validate flag](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L186-L203), [recursive validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L266-L334))
- Python agent asset loader security:
  - when `safe_mode=True`, `Env` PowerFx env access is blocked
  - `safe_mode=False` is recommended only for trusted YAML
  - `additionalProperties=false` is enforced on outputSchema nested object nodes  
  ([safe_mode docs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_loader.py#L236-L245), [normalize object schemas additionalProperties false](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_models.py#L239-L249))
- The Python HTTP default handler security note explicitly states **no URL filtering / no SSRF protection**. Production deployments must install a custom allowlist handler. The Python MCP default handler carries the same security note. ([HTTP security note](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_http_handler.py#L1-L18), [MCP security note](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_mcp_handler.py#L16-L24))
- The .NET `DefaultMcpToolHandler` does not explicitly discuss SSRF but implements defense-in-depth through disabled auto-redirects, disabled cookies, an origin-pinning handler, and forced `StreamableHttp`. This appears to be a more attack-surface-reducing security posture than the Python default MCP handler. ([origin pinning and redirect/cookie restrictions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative.Mcp/DefaultMcpToolHandler.cs#L206-L247))
- The .NET `InvokeMcpToolExecutor` does not include transport headers in the approval request. Python also surfaces only names rather than values for headers. That is, both sides aim to avoid secret header leakage on the approval surface. ([.NET no headers in approval request](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/ObjectModel/InvokeMcpToolExecutor.cs#L97-L105), [Python header names only](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_mcp.py#L13-L17))
- Python path safety tests pin the rejection of unsafe object-attribute traversal, making declarative state path resolution a security boundary rather than a convenience feature. ([state path safety tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_state_path_safety.py#L90-L133))

## .NET/Python implementation differences

- **Whether an agent assets loader exists**: Python has the experimental `AgentFactory` and a rich asset schema model, but the .NET inspected scope centers on the workflow YAML loader and the `ResponseAgentProvider` abstraction rather than a generic YAML prompt-agent loader. ([Python AgentFactory](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_loader.py#L143-L189), [.NET ResponseAgentProvider responses-centric abstraction](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/ResponseAgentProvider.cs#L13-L21))
- **workflow definition shape**: Python `WorkflowFactory` allows both top-level `actions` and `trigger.actions`, but the .NET builder centers on an object-model route that reads an `AdaptiveDialog` root. ([Python _get_actions_from_def](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_factory.py#L521-L547), [.NET ReadWorkflow root alias](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/DeclarativeWorkflowBuilder.cs#L90-L101))
- **state safety**: Python declarative implements safe path segments and `Env` allowlisting as a first-class security feature and pins them with tests. In the inspected .NET scope, an equivalent path safety layer does not appear as a separate public contract. ([Python path/env safety](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L70-L123), [Python path safety tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_state_path_safety.py#L90-L133))
- **code generation**: .NET uses a route/protocol Roslyn source generator together with declarative checkpoint JSON source generation. Python uses a runtime introspection + dynamic serialization model. ([.NET Roslyn generator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/ExecutorRouteGenerator.cs#L16-L75), [.NET DeclarativeWorkflowJsonOptions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/DeclarativeWorkflowJsonOptions.cs#L41-L77), [Python runtime model normalization](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_models.py#L116-L138))

## Java decisions

- Java declarative should place **workflow declarative** and **agent asset declarative** in separate modules/packages. Because the maturity of the two surfaces can differ as in Python, it is safer to begin with `workflow-declarative` as a stable core addon and `agent-assets-declarative` as preview/experimental. ([Python README split](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/README.md#L11-L18))
- The Java workflow DSL must clearly separate the 3 stages of **schema AST → normalized model → graph lowering**.
  - Python `_models.py` `type→kind` / nested schema normalization
  - Python `_declarative_builder.py` graph lowering
  - .NET `WorkflowActionVisitor` node decomposition  
  Mixing these three layers makes validation, IDE tooling, and AOT support harder. ([Python schema normalization](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_models.py#L206-L302), [Python graph lowering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_builder.py#L186-L239), [.NET graph lowering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/Interpreter/WorkflowActionVisitor.cs#L66-L296))
- Java declarative state must include **safe path resolution** and **Env allowlisting** as default security features, as in Python. Using only a generic `Map<String,Object>` creates vulnerabilities at expression/path boundaries. ([Python Env allowlist](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L70-L123), [Python path safety enforcement](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_declarative_base.py#L337-L497))
- The Java action handler SPI must expose typed interfaces (`HttpRequestHandler`, `McpToolHandler`, `AgentProvider`) as a public contract in the same manner as `.NET`, and must explicitly separate production defaults from security-hardened custom implementations. The way Python default MCP/HTTP handlers document “no SSRF protection” is also worth referencing. ([.NET IHttpRequestHandler](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/IHttpRequestHandler.cs#L11-L29), [.NET IMcpToolHandler](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/IMcpToolHandler.cs#L10-L41), [Python HTTP security note](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_http_handler.py#L1-L18), [Python MCP security note](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_mcp_handler.py#L16-L24))
- If Java has AOT/native-image goals, it is advisable to place **source-generated serialization metadata for declarative checkpoint payloads** in a separate module, as in `.NET`. Python-style dynamic object encoding is disadvantageous in a native-image environment. ([DeclarativeWorkflowJsonOptions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/DeclarativeWorkflowJsonOptions.cs#L15-L77))
- Java tool approval/MCP approval must treat the **`original_request` payload as the source of truth**, as in Python declarative tests. A resumed invocation must not re-read mutable workflow state and use values that changed while waiting for approval. ([Python approval binding tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L170-L220), [.NET InvokeRegisteredFunctionAsync uses snapshot](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Declarative/ObjectModel/InvokeFunctionToolExecutor.cs#L398-L440))
