## Purpose and boundary

### Purpose

- This feature serves the following four purposes.
  1. **Nesting a workflow inside another workflow** to enable hierarchical composition.
  2. **Exposing a workflow as an agent surface** to make it reusable in the agent ecosystem.
  3. **Aligning session/state/checkpoint boundaries** with composition boundaries.
  4. **Re-mapping stream/error/request-info across boundaries**.  
  In .NET, `WorkflowHostExecutor` and `WorkflowHostAgent`/`WorkflowSession` play this role; in Python, `WorkflowExecutor`, `Workflow.as_agent()`, and `FunctionalWorkflowAgent` do. ([.NET WorkflowHostExecutor role](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L17-L44), [.NET WorkflowHostAgent role](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostAgent.cs#L16-L27), [Python WorkflowExecutor overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L106-L170), [Python FunctionalWorkflowAgent overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1331-L1354))

### Boundary

- The included scope is as follows.
  - subworkflow binding and ownership
  - subworkflow ↔ parent output/request/error forwarding
  - workflow-as-agent session/response composition
  - functional workflow workflow/step composition, replay, cache, HITL restart
- The excluded scope is as follows.
  - the general graph builder/edge topology itself
  - the base superstep scheduler of the general workflow runtime
  - per-orchestration business policy
  - declarative YAML lowering in general  
  Based on the inspected code, the direct scope of this document is `.NET`'s `SubworkflowBinding.cs`, `WorkflowHostExecutor.cs`, `WorkflowHostAgent.cs`, `WorkflowSession.cs`, Python's `_workflow_executor.py`, `as_agent` in `_workflow.py`, `_functional.py`, and their tests. ([.NET SubworkflowBinding](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SubworkflowBinding.cs#L17-L46), [.NET WorkflowHostExecutor](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L17-L321), [.NET WorkflowSession](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L19-L768), [Python WorkflowExecutor](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L106-L610), [Python functional workflow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1-L1572))

## Detailed execution flow

### 1. .NET SubworkflowBinding and WorkflowHostExecutor

- `SubworkflowBinding` is the public composition entry that wraps a child workflow as an executor binding. At construction time, `CreateWorkflowExecutorFactory(...)` **first grants an ownership token to the child workflow**, after which it creates the `WorkflowHostExecutor`. This binding is declared with `IsSharedInstance=false`, `SupportsConcurrentSharedExecution=true`, and `SupportsResetting=false`. That is, the child workflow is not reused directly like a shared child instance; the host executor mediates it. ([SubworkflowBinding factory and ownership](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SubworkflowBinding.cs#L17-L46))
- `WorkflowHostExecutor` acts as the runtime proxy for the child workflow inside the parent workflow.  
  - `ConfigureProtocol(...)` exposes the child workflow protocol's yield types as its own yields and uses a catch-all route to interpret every message from the parent as either a child workflow start input or an `ExternalResponse`.  
  - If an active child run already exists, it enqueues the incoming message to the existing run; otherwise it starts a new subworkflow streaming run.  
  ([WorkflowHostExecutor protocol](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L46-L76), [EnsureRunSendMessageAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L104-L164))
- When the child workflow emits an external request, `WorkflowHostExecutor.ForwardWorkflowEventAsync(...)` sends it back to the parent join context. It qualifies the port id as `"{hostExecutorId}.{childPortId}"` to secure response correlation on the parent side and internally stores the original `RequestPortInfo` in `_pendingResponsePorts`. Conversely, `CheckAndUnqualifyResponse(...)` maps responses returned from the parent back to the child port id. ([qualify/unqualify response port ids](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L166-L186), [request forwarding and pendingResponsePorts](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L201-L205))
- Child workflow output forwarding is controlled by executor option boundaries. When a `WorkflowOutputEvent` is received:
  - if `AutoSendMessageHandlerResultObject=true`, forward to the parent workflow as a message
  - if `AutoYieldOutputHandlerResultObject=true`, yield as parent workflow output  
  Accordingly, whether to treat child output as a message internal to the parent or as a caller-facing output external to the parent is determined by the host executor options. ([child output forwarding](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L209-L223))
- Child workflow internal lifecycle events (`WorkflowStartedEvent`, `SuperStepStartedEvent`, `SuperStepCompletedEvent`) are not forwarded to the parent. In contrast, `WorkflowErrorEvent` is wrapped as `SubworkflowErrorEvent`, and warning strings are wrapped as `SubworkflowWarningEvent` and delivered to the parent. That is, the composition boundary partially hides and partially reformats the raw child observability surface. ([event boundary filtering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L188-L249))
- On checkpoint restore, `WorkflowHostExecutor` restores the child-dedicated `InMemoryCheckpointManager` and `_pendingResponsePorts` from state. If the checkpoint manager instance has changed, it resets the active child run stack with `ResetAsync()` and then resumes the child run with `EnsureRunSendMessageAsync(resume:true)`. ([host executor checkpoint restore](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L256-L321))

### 2. .NET workflow-as-agent: WorkflowHostAgent + WorkflowSession

- The public `WorkflowHostingExtensions.AsAIAgent(...)` creates a `WorkflowHostAgent`. This agent validates in advance via `DescribeProtocolAsync()` that the workflow uses the chat protocol, and can attach implicit in-memory checkpointing in-proc even when the execution environment lacks checkpointing. ([AsAIAgent public extension](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostingExtensions.cs#L13-L38), [WorkflowHostAgent constructor and validation setup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostAgent.cs#L27-L52), [ValidateWorkflowAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostAgent.cs#L70-L74))
- `WorkflowSession` is the actual session boundary. This session holds the following.
  - current `LastCheckpoint`
  - optional in-memory checkpoint manager
  - `StateBag`
  - `_pendingRequests` map  
  That is, a workflow-as-agent can include workflow checkpointing state inside agent session serialization. ([WorkflowSession fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L19-L52), [session deserialize ctor](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L98-L130), [SessionState serialization payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L755-L767))
- When a session is restored, `CreateOrResumeRunAsync(...)` creates either a fresh run or a resume run depending on whether `LastCheckpoint` exists. The resume path uses an internal resume API that **suppresses pending request republishing**. The reason is that `WorkflowSession` separately manages pending requests and must convert incoming agent-side responses back to `ExternalResponse`. ([CreateOrResumeRunAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L176-L206))
- `SendMessagesWithResponseConversionAsync(...)` is the core boundary of workflow-as-agent composition. This method scans incoming agent-side `ChatMessage` contents and:
  - ordinary chat messages as regular messages
  - those matching pending requests, such as `FunctionResultContent` / `ToolApprovalResponseContent`, as `ExternalResponse`  
  separates them. It sends regular messages first, external responses afterwards, and removes processed pending requests from the session map. ([response conversion split](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L215-L289))
- Workflow stage streaming is performed by `InvokeStageAsync(...)`. This method converts the raw `WorkflowEvent`s of the child `StreamingRun` into agent-facing `AgentResponseUpdate`s, applying the following rules per boundary.
  - `AgentResponseUpdateEvent` → forward as-is
  - `RequestInfoEvent` → convert to AIContent request content and register in `_pendingRequests`
  - `WorkflowErrorEvent` / `ExecutorFailedEvent` → expose as `ErrorContent`, hide internal graph ids
  - `SuperStepCompletedEvent` → observability update only
  - `AgentResponseEvent` → suppress already-streamed message ids to prevent duplication
  - `WorkflowOutputEvent` → include or exclude based on `includeWorkflowOutputsInResponse` or terminal-output status  
  ([InvokeStageAsync event translation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L443-L647))
- `WorkflowHostAgent.RunCoreAsync(...)` and `RunCoreStreamingAsync(...)` ultimately consume `WorkflowSession.InvokeStageAsync(...)`. The merged final response is built from terminal workflow outputs if present, or from all updates otherwise. That is, the final response boundary of workflow-as-agent is jointly determined by workflow output designation and host options. ([RunCoreAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostAgent.cs#L109-L133), [RunCoreStreamingAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostAgent.cs#L135-L158), [terminal output merge policy](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostAgent.cs#L160-L195))

### 3. Python graph composition: WorkflowExecutor

- Python `WorkflowExecutor` makes a child workflow operate as a single executor inside a parent workflow. The official docstring describes the character of this type at almost specification level.  
  - output forwarding
  - request/response coordination
  - failure propagation
  - child workflow checkpoint embedding  
  All of these constitute the contract of this type. ([WorkflowExecutor overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L106-L246))
- The input types of `WorkflowExecutor` are the child workflow's start executor input types plus `SubWorkflowResponseMessage`, and the output types are the child workflow's output types plus `SubWorkflowRequestMessage` when necessary. That is, the type boundary nearly inherits the child workflow signature as-is. ([input/output type contract in doc](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L171-L191), [input_types impl](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L289-L302), [output_types impl](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L304-L320))
- `process_workflow(...)` executes the child workflow with new input. At this point it reads `WORKFLOW_RUN_KWARGS_KEY` from the parent workflow state to pass function/client kwargs to the child workflow, and if the child workflow receives new input while it still has pending requests, it leaves a warning. The child result is processed by `_process_workflow_result(...)`. ([process_workflow start path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L348-L405))
- `_process_workflow_result(...)` makes the composition boundary explicit.
  - If `allow_direct_output=False`, sends child outputs as parent messages.
  - If `allow_direct_output=True`, yields child outputs directly as parent workflow output.
  - Child intermediate outputs are re-emitted as `type='intermediate'` events, bypassing the parent's own output classifier.
  - Child `request_info` is forwarded as a parent external request if `_propagate_request=True`, or wrapped as `SubWorkflowRequestMessage` otherwise.
  - Child failed state is promoted to a parent error event.  
  ([process result boundaries](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L498-L589))
- `_handle_response(...)` uses the child workflow's pending request map as the source-of-truth. Unknown or already-handled request ids are ignored after a warning; known requests re-enter the child workflow with `responses={request_id: response}`. ([handle response source-of-truth](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L591-L610))
- For checkpointing, `WorkflowExecutor` itself does not maintain separate pending-request bookkeeping; instead it stores the child workflow's in-memory checkpoint object directly in the parent executor state. Restore also returns the child checkpoint directly to the child runner. The legacy checkpoint fallback supports only pending request republishing. ([checkpoint embed](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L451-L470), [legacy fallback](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L472-L497))

### 4. Python workflow-as-agent: Workflow.as_agent()

- The agent adapter entrypoint for a graph workflow is `Workflow.as_agent(...)`. The docstring states that this adapter normalizes string/`Message`/list input to `list[Message]` and passes it to the workflow start executor, and explicitly notes that it fails if the start executor cannot accept `list[Message]`. ([Workflow.as_agent contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1193-L1234))
- How intermediate workflow events are delivered when passing through the agent adapter is pinned by tests. The output of an intermediate-designated executor is delivered as `AgentResponseUpdate`, hidden yields are not surfaced, and `Message.additional_properties` is also preserved in the intermediate forwarding path. ([intermediate forwarding test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L32-L67), [hidden yields non-streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L99-L120), [hidden yields streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L122-L145), [additional_properties preserved](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L170-L206))

### 5. Python functional workflow API

- Functional workflow is an experimental API that allows using a plain async function as a workflow without graph compilation. `@workflow` wraps an async function as a `FunctionalWorkflow`, and `@step` provides an optional tracked step wrapper. `RunContext` provides HITL, custom events, and key/value state. ([functional workflow overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L10-L31), [RunContext overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L107-L153), [@workflow decorator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1260-L1323))
- The basic re-execution boundary of functional composition is `StepWrapper`.  
  - The step cache key is `(step_name, call_index)`.
  - On a cache hit, only `executor_bypassed` is emitted instead of the live execution pair (`executor_invoked`/`executor_completed`).
  - If a `RunContext` parameter is present, it is injected automatically.
  - After a live step completes, a per-step checkpoint can be saved if configured storage is present.  
  ([StepWrapper semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L411-L552))
- `RunContext.request_info(...)` suspends the workflow by throwing an internal `WorkflowInterrupted` on initial execution, and directly returns the response provided by the caller on replay. If `request_id` is omitted, a deterministic `auto::<index>` id is created. Also, while user state is a simple dict, keys with a leading underscore are prohibited as they are reserved for framework bookkeeping. ([WorkflowInterrupted BaseException](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L87-L99), [RunContext.request_info](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L193-L250), [RunContext state API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L263-L302))
- `FunctionalWorkflow` computes `graph_signature_hash` by mixing the workflow name, discovered step names, and the function bytecode/co_names digest. On restore, if the checkpoint's hash differs, it fails as an incompatible workflow. ([FunctionalWorkflow init and graph_signature_hash](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L671-L699), [signature hash implementation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1162-L1182), [checkpoint signature mismatch restore](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L930-L944))
- The state boundary on functional workflow restore is as follows.
  - On checkpoint restore, `_step_cache`, `_step_cache_auto_request_info_counts`, user state, pending request_info events, and `_original_message` are restored.
  - On responses-only replay, `_last_message` and the last step cache are taken from memory.
  - On live execution/interrupt/final completion, `_save_checkpoint(...)` includes step cache and `_original_message` in the checkpoint state.  
  ([restore state on checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L925-L980), [live execution and interrupt checkpoints](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L999-L1067), [save_checkpoint payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1142-L1160))
- Functional workflow streaming is not true per-token streaming. The code comment states that events generated during `_execute()` are buffered and yielded all at once after the user function finishes. That is, its boundary differs from the event-as-produced streaming of graph workflows. ([not true streaming note](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1011-L1016))
- `FunctionalWorkflowAgent` wraps a functional workflow as an agent-compatible surface. `request_info` events are converted to `function_approval_request` content and exposed to the agent caller, and kept in the `pending_requests` map. In non-streaming mode they are converted to a final `AgentResponse`; in streaming mode to a `ResponseStream[AgentResponseUpdate, AgentResponse]`. ([FunctionalWorkflowAgent overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1331-L1354), [FunctionalWorkflowAgent.run](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1382-L1450), [streaming request_info to approval request](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1492-L1544), [non-streaming result to AgentResponse](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1545-L1572))

## State and persistence

### .NET

- At the subworkflow boundary, ownership is preempted by `SubworkflowBinding`. This structurally prevents direct graph misuse where multiple parents/subworkflows simultaneously share the same child workflow. ([SubworkflowBinding ownership token](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SubworkflowBinding.cs#L23-L35))
- The persistent state of `WorkflowHostExecutor` consists of two main parts.
  1. a child-dedicated `InMemoryCheckpointManager`
  2. `_pendingResponsePorts`  
  On restore, if the checkpoint manager instance has changed, the existing child run stack is cleaned up with `ResetAsync()` and then resumed. ([host executor checkpoint state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L256-L294), [reset on manager change](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L296-L321))
- `WorkflowSession` is the workflow-as-agent session boundary. The serialized `SessionState` includes `SessionId`, `LastCheckpoint`, optional `CheckpointManager`, `StateBag`, and `PendingRequests`. That is, agent session serialization absorbs workflow continuation state. ([session ctor and pending requests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L70-L96), [deserialize ctor](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L98-L130), [SessionState payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L755-L767))

### Python

- The graph-based `WorkflowExecutor` directly embeds the child checkpoint object into the parent executor state. This approach allows child shared state, messages, and pending request_info events to be restored together with only a single parent checkpoint, even without a child storage backend. ([sub_workflow_checkpoint save](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L451-L461), [sub_workflow_checkpoint restore](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L464-L470))
- Functional workflow has in-memory replay state rather than an external runner context as in a graph. `_last_message`, `_last_step_cache`, `_last_step_cache_auto_request_info_counts`, and `_last_pending_request_ids` constitute the state for responses-only replay. If checkpoint storage is present, `_save_checkpoint(...)` also exports this to an external checkpoint. ([FunctionalWorkflow replay state fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L682-L699), [checkpoint save payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1142-L1160))
- Functional `RunContext` user state prohibits underscore-prefixed keys. This is a design choice to avoid collisions with internal keys in the checkpoint payload, such as framework bookkeeping keys (`_step_cache`, `_original_message`). ([underscore-prefixed user state forbidden](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L278-L302))

## Concurrency, streaming, and cancellation

### Concurrency boundary

- In .NET, the child workflow is created via `InProcessRunner.CreateSubworkflowRunner(...)` inside the parent `WorkflowHostExecutor` and attached to the join context. If an active run already exists on the same host executor, new input is enqueued to the existing run. Therefore, child workflow concurrency is serialized at the parent host executor boundary. ([EnsureRunnerAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L81-L102), [EnsureRunSendMessageAsync reuse existing run](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L104-L116))
- Because Python `WorkflowExecutor` maintains a single shared child workflow instance, if new input arrives while pending requests remain, it leaves a warning. The docstring warns that this overlap is permitted but is safe only when the child workflow and executors are stateless. ([overlapping execution warning in docs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L198-L205), [warning in process_workflow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L359-L371))
- Python functional workflow has a whole-workflow concurrency guard. If `_is_running` is true, a second run is rejected with a `RuntimeError`. Tests pin this as well. ([FunctionalWorkflow _ensure_not_running](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1246-L1254), [concurrent run test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L857-L872))

### Streaming boundary

- .NET `WorkflowSession.InvokeStageAsync(...)` converts the raw `StreamingRun` stream of the child workflow into an agent-facing `AgentResponseUpdate` stream. During this process, it suppresses duplicate message ids between `AgentResponseUpdateEvent`s already sent to the stream and the completion `AgentResponseEvent`. That is, at the streaming boundary a “raw workflow events → de-duplicated agent updates” reformatting takes place. ([InvokeStageAsync agent update streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L482-L505), [streamed message dedup in AgentResponseEvent](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L552-L590))
- Python graph `Workflow.as_agent()` can forward intermediate outputs as agent updates, and does not forward hidden yields. That is, graph output designation directly affects the agent streaming boundary. Tests pin this contract. ([intermediate forwarded](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L32-L67), [hidden yields hidden in streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L122-L145))
- Python functional workflow is “streaming” but not true live streaming. Step/workflow events accumulate in a buffer during execution and are replayed all at once after the workflow function completes. In contrast, `FunctionalWorkflowAgent.run(stream=True)` translates these buffered workflow events back into an `AgentResponseUpdate` stream. ([functional streaming not true streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1011-L1016), [FunctionalWorkflowAgent streaming adapter](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1492-L1520))

### Cancellation boundary

- In the inspected `.NET` composition code, a child run is cleaned up via `WorkflowHostExecutor.ResetAsync()` / `DisposeAsync()`. It disposes active streaming runs, disconnects active child runner event subscriptions, and detaches from the join context. This boundary means the parent owns the child lifecycle. ([WorkflowHostExecutor reset/dispose](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L296-L321))
- Because Python functional workflow's HITL interruption uses `WorkflowInterrupted` which inherits `BaseException`, an `except Exception:` block inside the user workflow cannot swallow the composition control signal. This safely guarantees a non-local control boundary similar to cancellation/interruption. Tests pin this as well. ([WorkflowInterrupted BaseException](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L87-L99), [except Exception should not catch interruption](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L1034-L1053))

## Errors, validation, and security

- .NET workflow-as-agent re-restricts error exposure at the boundary. `WorkflowSession.InvokeStageAsync(...)` converts `WorkflowErrorEvent`/`ExecutorFailedEvent` to `ErrorContent`, but if `includeExceptionDetails=false`, it surfaces only a generic message and hides internal graph identifiers. ([workflow error mapping](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L508-L545))
- .NET `WorkflowHostExecutor` does not expose child workflow internal lifecycle events to the parent as-is. Errors are wrapped as `SubworkflowErrorEvent` and warnings as `SubworkflowWarningEvent`. This constitutes both an observability boundary and an information-hiding boundary. ([subworkflow event filtering/wrapping](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L188-L249))
- .NET workflow-as-agent checkpoint identity fails to resume if inner agent ids/names change. Tests pin that resume is possible after reconstruction with stable inner ids, but that random ids or renamed inner agents fail with `InvalidDataException`. ([stable inner ids resume](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowAgentCheckpointIdentityTests.cs#L31-L59), [random inner ids fail](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowAgentCheckpointIdentityTests.cs#L61-L87), [stable ids but changed names fail](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowAgentCheckpointIdentityTests.cs#L89-L112))
- Python `WorkflowExecutor` ignores responses for unknown/already-handled request ids after a warning. That is, the child workflow pending request map is the sole source-of-truth. ([unknown response ignored](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L597-L610))
- Python functional workflow refuses restore on a checkpoint signature mismatch. The hash is computed by mixing workflow name + discovered steps + code digest. ([signature mismatch error](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L930-L944), [signature hash computation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1162-L1182))
- Python functional step cache import treats malformed cache keys/indexes as corruption and fails. This is a defense against incompatible or corrupted checkpoints. ([corrupted step cache import checks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L377-L403), [tests for malformed cache import](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L1061-L1091))

## .NET/Python differences

- **public composition model**: .NET provides an explicit public `AsAIAgent(...)` extension + public `SubworkflowBinding`, while the actual runtime proxy is handled by internal `WorkflowHostExecutor`/`WorkflowSession`. Python graph composition is more direct, with public `WorkflowExecutor` and `Workflow.as_agent()`. ([.NET AsAIAgent](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostingExtensions.cs#L13-L38), [.NET SubworkflowBinding](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SubworkflowBinding.cs#L17-L46), [Python WorkflowExecutor](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L248-L279), [Python Workflow.as_agent](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1193-L1234))
- **session boundary**: In .NET workflow-as-agent, an explicit `WorkflowSession` object creates the session serialization boundary, encompassing the checkpoint manager, last checkpoint, and pending requests. Python graph workflow-as-agent, within the inspected scope, relies more on adapter/underlying workflow instance semantics than on a separate workflow session class. Functional workflow has yet another in-memory replay state. ([.NET WorkflowSession state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L19-L52), [functional replay state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L682-L699))
- **subworkflow checkpointing**: The .NET child workflow stores a dedicated in-memory checkpoint manager inside the parent host executor state, whereas Python `WorkflowExecutor` embeds the child `WorkflowCheckpoint` object itself into the parent executor checkpoint state. ([.NET host executor checkpoint manager state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L256-L294), [Python sub_workflow_checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L451-L470))
- **streaming boundary**: .NET workflow-as-agent converts child workflow events to live `AgentResponseUpdate` while removing duplicate streamed messages. Python functional workflow is not “true streaming” because it replays events after buffering. ([.NET live translation and dedup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L482-L590), [functional not true streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1011-L1016))
- **functional composition**: Python has an experimental `@workflow`/`@step` functional API, but within the inspected `.NET Microsoft.Agents.AI.Workflows*` scope, composition is implemented in graph/subworkflow/agent-wrapper form. The Python functional API treats code-shape hash and step cache as part of the composition boundary. ([Python functional API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1-L31), [FunctionalWorkflow signature hash](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1162-L1182))

## Documentation differences

- The Python graph `WorkflowExecutor` docstring describes implementation responsibilities in considerable detail, and the actual code closely follows that contract. In contrast, looking only at the .NET public `AsAIAgent(...)` does not reveal the actual behavior of the composition boundary; one must read the `WorkflowHostExecutor`/`WorkflowSession` internal implementation to discover the pending request translation, terminal output merge, and error masking rules. Accordingly, in .NET, composition has a **higher reliance on source implementation than on public docs**. ([.NET AsAIAgent surface only](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowHostingExtensions.cs#L13-L38), [.NET WorkflowSession actual boundary logic](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L443-L647), [Python WorkflowExecutor doc + code](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L106-L246))
- The Python functional workflow documentation states that “streaming mode” is supported, but the code comments clearly state that the current implementation is buffered-after-completion replay. Therefore, interpreted code-first, functional workflow streaming does not have the same meaning as graph workflow streaming. ([functional run doc](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L772-L805), [not true streaming note](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1011-L1016))

## Java decisions

- For Java composition, it is advisable to design **graph workflow composition** and **functional composition** as separate API families. While both can be placed in one package as in Python, the stability level (stable vs experimental) must be clearly distinguished. Starting graph-based `WorkflowExecutor`/`Workflow.asAgent()` as stable core and the functional workflow DSL as preview/experimental is the safer approach. ([Python functional experimental](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L3-L9), [Python core graph as_agent stable package](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/pyproject.toml#L13-L24))
- Java subworkflow composition is safer modeled after `.NET` with the **ownership token + host executor** model. Allowing a child workflow instance to be freely shared like any executor blurs lifecycle, checkpoint, and overlapping request boundaries. ([.NET SubworkflowBinding ownership](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SubworkflowBinding.cs#L23-L35), [.NET WorkflowHostExecutor reset/lifecycle ownership](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L296-L321))
- Java workflow-as-agent must store **checkpoint pointer + pending request map + option flags** together in a session object. As with .NET `WorkflowSession`, agent-session serialization must contain the workflow continuation state for reconstruction/resume to be possible. ([.NET WorkflowSession fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L19-L52), [SessionState payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowSession.cs#L755-L767))
- If a Java functional workflow is introduced, the three design choices of the Python functional API are worth adopting directly.
  1. a non-local control signal equivalent to `WorkflowInterrupted extends BaseException`
  2. a deterministic step cache based on `(step_name, call_index)`
  3. checkpoint compatibility based on code-shape hash  
  Without these three, step replay/HITL/restore will be unstable. ([WorkflowInterrupted](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L87-L99), [StepWrapper cache key/bypass](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L512-L549), [signature hash](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1162-L1182))
- The Java agent adapter should have a **common adapter contract for converting request_info to agent-surface approval content** for both graph and functional workflows. The Python functional agent already demonstrates this model. ([FunctionalWorkflowAgent request_info to approval content](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1522-L1543))

## Concrete acceptance scenarios

1. **When a child workflow is inserted as an executor, the parent must be able to selectively receive child output as either a message or an output.**  
   In Python, `allow_direct_output=False` means message forwarding, `True` means direct yield. In .NET, the host executor option combination serves the same role. ([Python direct output switch](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L524-L529), [.NET output forwarding options](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/WorkflowHostExecutor.cs#L209-L223))

2. **Child workflow request_info must be reformatted as either parent interception or external propagation.**  
   In Python, `propagate_request=False` means `SubWorkflowRequestMessage`, `True` means parent `request_info()`. ([Python request propagation switch](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L544-L557))

3. **Child workflow intermediate outputs must remain intermediate independently of the parent output designation.**  
   In Python, `WorkflowExecutor` re-emits them as `type='intermediate'`, bypassing the parent classifier. ([intermediate propagation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_executor.py#L531-L542))

4. **Workflow-as-agent must not include hidden yields in the final agent response.**  
   Graph workflow agent adapter tests pin hidden yield suppression. ([hidden yields non-streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L99-L120), [hidden yields streaming](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_agent_intermediate.py#L122-L145))

5. **Workflow-as-agent checkpoint resume must succeed only when inner agent identity is stable.**  
   .NET tests pin that resume succeeds with stable inner ids, and fails with random ids or renamed inner names. ([stable ids resume](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowAgentCheckpointIdentityTests.cs#L31-L59), [random ids fail](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowAgentCheckpointIdentityTests.cs#L61-L87), [renamed names fail](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowAgentCheckpointIdentityTests.cs#L89-L112))

6. **Functional workflow checkpoint restore must replay completed steps as `executor_bypassed` and not re-execute them.**  
   ([executor_bypassed on replay](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L1099-L1135))

7. **Functional workflow per-step checkpointing must enable crash recovery.**  
   Earlier steps must be skipped via cache replay, and only the next step that crashed must be re-executed. ([per-step checkpoint crash recovery](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L629-L672))

8. **An `except Exception:` inside a functional workflow must not catch a HITL interrupt.**  
   Because `WorkflowInterrupted` is a `BaseException`, it must fall into the pending request state. ([WorkflowInterrupted contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L87-L99), [test_except_exception_does_not_catch_interrupt](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L1034-L1053))

9. **The functional workflow agent adapter must surface request_info as function approval request content.**  
   The caller must find the request id in `pending_requests` and find `function_approval_request` content in agent response messages. ([FunctionalWorkflowAgent request_info conversion](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_functional.py#L1522-L1543), [agent HITL test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_functional_workflow.py#L1661-L1681))

10. **Subworkflow request interception must be scopeable per workflow.**  
    Python tests pin a scenario in which `workflow_a` and `workflow_b` use the same child definition but apply parent interception rules differently per workflow. ([workflow-scoped interception](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_sub_workflow.py#L268-L361))
