# 06-tool-approval

This document covers only **tool approval** in the Agent Framework. Specifically it describes the **user approval request/response types**, the **meaning of the approval-required tool wrapper**, the **middleware/state/rule model**, **argument-aware standing approval**, the **denial/error/resume flow**, and the **session linkage**. The **MCP approval protocol itself** and **workflow/HITL orchestration** belong to separate documents, so only the boundary is described here. Based on the reviewed source, .NET has two layers: (1) a **chat-client decorator layer** that reinforces the tool-approval request/response on top of `FunctionInvokingChatClient`, and (2) a **`ToolApprovalAgent` harness layer** that provides caller-facing “don’t ask again”/queueing. Python is divided into (1) the approval request/response semantics at the core `Content`/tool-loop level, and (2) the standing rule/queueing layer of the opt-in `ToolApprovalMiddleware`. ## Purpose

The purpose of the tool approval feature is **not to execute a model-selected tool call immediately and unconditionally**, but to surface particular calls for user approval, and then to bind the decision the user gave back to the **same logical tool call**, carrying out execution, denial, and even the storing of auto-approval rules. The .NET chat-client decorator strengthens the guarantee that “the approval request the model surfaced and the approval response the caller returned correspond to exactly the same call”, while the Python core/harness treats an approval request as user-input-required content and stores standing rules and queued requests in session state. [ApprovalResponseBindingChatClient.cs#L22-L38](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs#L22-L38) [ToolApprovalAgent.cs#L22-L50](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/Harness/ToolApproval/ToolApprovalAgent.cs#L22-L50) [_types.py#L1273-L1313](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_types.py#L1273-L1313) [_harness/_tool_approval.py#L343-L379](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L343-L379)

### Meaning of the approval-required tool wrapper

#### Python

- In the Python core, whether a tool is approval-required is expressed by whether `FunctionTool.approval_mode` is `"always_require"` or `"never_require"`. The default is `"never_require"`. ## Tool approval rule / standing approval model

### Python

- `ToolApprovalRule` has `tool_name`, an optional `arguments`, and an optional `server_label`. With `arguments is None` it is a tool-wide rule, and a non-null empty dict is a **no-argument call only** rule. [_harness/_tool_approval.py#L86-L117](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L86-L117)
- An argument-aware rule builds a canonicalized string dict with `_serialize_arguments(function_call)` and matches exactly. [_harness/_tool_approval.py#L41-L58](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L41-L58) [_harness/_tool_approval.py#L301-L320](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L301-L320)
- The hosted-tool boundary is isolated by `server_label`. A standing rule matches only when the `server_label` is the same, even for the same tool name. [_harness/_tool_approval.py#L61-L64](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L61-L64) [_harness/_tool_approval.py#L313-L320](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L313-L320)

- The .NET `ToolApprovalRule` has only `ToolName` and an optional `Arguments`. `Arguments == null` is a tool-level rule and a non-null empty dictionary is a no-argument exact rule. ## Detailed middleware / state / rules execution flow

### .NET lower-level: binding & bypass decorators

1. `ApprovalResponseBindingChatClient` records the `ToolApprovalRequestContent` the model surfaced in the outbound response into session state. [ApprovalResponseBindingChatClient.cs#L395-L444](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs#L395-L444)  
2. On the next inbound turn, the `ToolApprovalResponseContent` sent by the caller is matched against the known request lookup. When there is no known request it is dropped and only a warning is logged. [ApprovalResponseBindingChatClient.cs#L163-L202](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs#L163-L202) [ApprovalResponseBindingChatClient.cs#L247-L289](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs#L247-L289)  
3. When the request id matches, the response's `ToolCall` is rebound to the model-originated call of the surfaced request. Even if the caller swaps the tool name/arguments, the executed call is therefore identical to the surfaced request. [ApprovalResponseBindingChatClient.cs#L262-L279](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs#L262-L279)  
4. `ApprovalNotRequiredFunctionBypassingChatClient` stores only the non-approval-required requests of a mixed approval batch in the session and removes them from the response. On the next turn it re-injects them as approved responses. [ApprovalNotRequiredFunctionBypassingChatClient.cs#L23-L34](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalNotRequiredFunctionBypassingChatClient.cs#L23-L34) [ApprovalNotRequiredFunctionBypassingChatClient.cs#L163-L186](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalNotRequiredFunctionBypassingChatClient.cs#L163-L186) [ApprovalNotRequiredFunctionBypassingChatClient.cs#L229-L320](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalNotRequiredFunctionBypassingChatClient.cs#L229-L320)

## Java decisions

- Java is better off keeping **the approval request/response as core-owned content subtypes** as Python does. Only then does the caller-facing API stay provider-neutral and the denial/result materialization stay unified as core semantics. [_types.py#L1272-L1362](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_types.py#L1272-L1362)
- At the same time a design that **separates two layers** as .NET does is useful: dividing the lower-level approval binding/forgery prevention seam from the higher-level standing-rule/queueing middleware lets the basic safety mechanism and the UX-oriented “don’t ask again” policy be composed independently. [ApprovalResponseBindingChatClient.cs#L15-L45](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/ChatClient/ApprovalResponseBindingChatClient.cs#L15-L45) [ToolApprovalAgent.cs#L16-L50](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/Harness/ToolApproval/ToolApprovalAgent.cs#L16-L50)
- For the standing rule, a `toolName + exactArguments + optional hostBoundary` structure as in Python is recommended. Because no rule field corresponding to `server_label` is visible in the reviewed .NET harness, it is safer for Java to include the boundary field from the start in order to prevent cross-host approval leakage. [_harness/_tool_approval.py#L61-L64](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L61-L64) [_harness/_tool_approval.py#L91-L117](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_harness/_tool_approval.py#L91-L117)
- For the denial semantics, leaving a **synthetic terminal result** as Python does is more transparent than a silent drop, because the caller, the LLM, and logging can all see the same failure artifact. [_tools.py#L2443-L2453](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_tools.py#L2443-L2453)
- A runaway auto-approval chain must have its own cap, like .NET's `MaxAutoApprovalIterations`. If a heuristic/standing rule allows an infinite loop, billable model calls can explode. [ToolApprovalAgentOptions.cs#L50-L68](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI/Harness/ToolApproval/ToolApprovalAgentOptions.cs#L50-L68)

[_tools.py#L2443-L2453](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_tools.py#L2443-L2453) [test_harness_tool_approval.py#L92-L104](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/core/test_harness_tool_approval.py#L92-L104)
