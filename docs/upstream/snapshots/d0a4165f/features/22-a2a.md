# 22. A2A

## Scope

This document covers **A2A(Agent2Agent) integration and hosting** in Microsoft Agent Framework. Specifically, it includes the following.

- **client/agent integration** that wraps a remote A2A agent as an Agent Framework `AIAgent`
- **hosting integration** that exposes a local Agent Framework agent via the A2A protocol
- semantics and mapping of **AgentCard**, **Message**, **Task**, and **Artifact**
- streaming, continuation token, and poll/subscribe boundaries
- session/state and identity/auth boundaries
- .NET / Python implementation differences
- conformance tests
- Java design decisions

Conversely, the general theory of generic hosting lifecycle, store abstraction, and workflow checkpoint is within the scope of a separate generic hosting document; only A2A-specific semantics and hosting integration points are covered here. The details of OpenAI Responses, AG-UI, MCP, Foundry Hosted Agents, and Telegram/ChatKit are also within the scope of separate documents. (Source: [Python A2A README](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L9-L28), [Python hosting-a2a README](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/README.md#L1-L10), [.NET Hosting.A2A registration docs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AServerServiceCollectionExtensions.cs#L22-L31))

## Summary

A2A is divided into two layers in this codebase. The first is **client/agent integration that treats a remote A2A agent like a local `AIAgent`**, and the second is **hosting integration that exposes a local Agent Framework target as an A2A protocol endpoint**. In .NET, `Microsoft.Agents.AI.A2A` is the preview client/agent package, and `Microsoft.Agents.AI.Hosting.A2A` + `...AspNetCore` is the preview hosting package. In Python, `agent-framework-a2a` is a beta-level full integration package (`A2AAgent`, `A2AExecutor`), and `agent-framework-hosting-a2a` is an alpha helper-only package that assists with app-owned native A2A server composition. On the card side, .NET splits the discovery path into `AgentCard.AsAIAgent(...)` and `IA2AClient.AsAIAgent(...)`, while the Python helper generates a public `AgentCard` via `AgentA2AAdapter`/`WorkflowA2AAdapter`. The Task/Artifact model is important in both languages; however, the .NET remote `A2AAgent` surfaces tasks as `AgentResponse`/`AgentResponseUpdate` with a continuation token, while the Python `A2AExecutor` projects local agent streaming output onto A2A task artifact updates using stable artifact id + append semantics. Regarding identity, `contextId`, `taskId`, and thread/session id are strictly routing handles, not bearer credentials, and a multi-user host must separately apply principal-scoped isolation. ## Purpose

The purpose of A2A support is to enable Agent Framework to **interoperate with the external A2A ecosystem**. This purpose is divided into two directions.

1. **Client direction**: A remote agent already exposed via A2A is used within Agent Framework as a single `AIAgent`.
2. **Hosting direction**: A local Agent Framework agent/workflow is exposed as an A2A server surface so that A2A-compliant clients can invoke it.

Here, “A2A integration” is not a simple text chat bridge; it includes the work of mapping A2A-specific concepts of **context**, **task**, **artifact**, **status update**, and **input-required continuation** to Agent Framework's `AgentSession`, `AgentResponse`, `AgentResponseUpdate`, and `ContinuationToken`. (Source: [.NET A2AAgent summary](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L18-L25), [Python A2A README A2AAgent section](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L9-L24), [Python A2AExecutor section](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L25-L48))

## Boundary

### What this feature does
- Converts an A2A client or card to an Agent Framework `AIAgent`.
- Converts Agent Framework `Message`/`Content` to A2A `Message`/`Part`.
- Converts A2A `Task`, `Artifact`, `TaskStatusUpdateEvent`, and `TaskArtifactUpdateEvent` to Agent Framework response/update.
- Helps manage the A2A task/message lifecycle on the local host.
- Provides card generation, mode validation, and agent/workflow conversion helpers for use by an app-owned native A2A server. (Source: [.NET A2AClientExtensions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/Extensions/A2AClientExtensions.cs#L10-L23), [.NET A2AAgentTaskExtensions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/Extensions/A2AAgentTaskExtensions.cs#L9-L59), [Python A2AExecutor summary](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_a2a_executor.py#L31-L42), [Python hosting-a2a README table](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/README.md#L11-L18))

### What this feature does not do
- Authentication/authorization for the A2A entry point
- Policy for approving caller-supplied `contextId`/`taskId` as trusted store keys
- Selection of the durable backend for the A2A task store
- non-A2A protocol routing
- The generic hosting/session store lifecycle itself

In particular, the Python helper package explicitly states that it does not provide “executor, task lifecycle, event queue, task store, routes, session policy, authentication, deployment”. The .NET hosting also documents that task/session identifiers must not be treated as authorization tokens. (Source: [Python hosting-a2a README does not provide lifecycle/routes/auth](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/README.md#L6-L10), [.NET hosting trust model](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AServerServiceCollectionExtensions.cs#L31-L47), [Python A2A security considerations](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L60-L64))

## Cards / discovery / agent integration

## .NET

### Direct configuration / private discovery
`.NET` provides a path that wraps an already-configured `IA2AClient` with `AsAIAgent(...)`. This path uses the A2A SDK client as-is, and models discovery as either already complete or as application-owned direct configuration. (Source: [.NET IA2AClient extension remarks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/Extensions/A2AClientExtensions.cs#L14-L39))

### Curated registry / catalog discovery
`AgentCard.AsAIAgent(...)` connects to the remote agent via `A2AClientFactory.Create(card, ...)`. That is, `AgentCard` is the client bootstrap artifact, and non-null options take precedence over the card's name and description. (Source: [.NET AgentCard extension create path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/Extensions/A2AAgentCardExtensions.cs#L19-L75))

## Python

### Full integration package
Python `A2AAgent` has three input paths.

- `url`
- `agent_card`
- existing `Client`

The default for `supported_protocol_bindings` is `["JSONRPC"]`; separate streaming and non-streaming clients are created, with a fallback to a minimal card if transport negotiation fails. This is a design in which the Python side **exposes transport negotiation more explicitly** than .NET. (Source: [Python A2AAgent init signature and defaults](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L221-L253), [streaming vs non-streaming clients and fallback](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L287-L320))

### Helper-only hosting package
Python `AgentA2AAdapter` and `WorkflowA2AAdapter` generate the public `AgentCard` to be exposed by an app-owned native A2A server. The card contains the following.

- name/description
- version
- default input/output modes
- `supported_interfaces`
- optional skills
- optional `AgentCapabilities`

Additionally, when `infer_skills=True`, skills can be automatically discovered from the Agent Framework `SkillsProvider`. (Source: [Python hosting-a2a README generate card](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/README.md#L96-L139), [AgentA2AAdapter get_card](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/agent_framework_hosting_a2a/_adapters.py#L130-L175))

## Hosting card boundary
`.NET` `MapA2AHttpJson` temporarily passes a stub `AgentCard` due to constraints in the A2A SDK. A code comment explains that the `GET {path}/card` endpoint is an SDK convenience endpoint, not part of the A2A spec, and therefore considers it safe to return a stub card. That is, the **.NET ASP.NET hosting layer has made a compromise on card publication to fit the reality of SDK integration rather than protocol fidelity**. (Source: [.NET MapA2AHttpJson stub card comment](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A.AspNetCore/A2AEndpointRouteBuilderExtensions.cs#L69-L80))

## Tasks / messages / artifacts

## .NET remote agent integration

### Message path
If the A2A remote response is a `Message`, `A2AAgent` converts it to an assistant `ChatMessage` to create an `AgentResponse`. The response id is `message.MessageId`, and metadata is preserved as `AdditionalProperties`. (Source: [.NET ConvertToAgentResponse(Message)](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L412-L423))

### Task path
If the A2A remote response is an `AgentTask`, `A2AAgent`:

- uses `task.Id` as the response id,
- converts `task.Artifacts` and `task.Status.GetUserInputRequests()` to `Messages`/`AIContents`, and
- creates a continuation token if the task state is `Submitted` or `Working`,
- maps to `FinishReason.Stop` if the task state is `Completed`.

That is, .NET's remote A2A integration is already **task-aware**. (Source: [.NET A2AAgentTaskExtensions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/Extensions/A2AAgentTaskExtensions.cs#L12-L59), [.NET ConvertToAgentResponse(AgentTask)](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L425-L437), [.NET CreateContinuationToken](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L402-L410))

### Artifact path
Artifacts are flattened into a sequence of assistant `ChatMessage` or `AIContent`. Metadata and raw representation are also preserved. (Source: [.NET A2AArtifactExtensions](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/Extensions/A2AArtifactExtensions.cs#L8-L26))

## Python remote agent integration

Python `A2AAgent` also reads the following payloads from the A2A stream.

- `message`
- `task`
- `status_update`
- `artifact_update`

`task`/`status_update`/`artifact_update` are each resolved as `AgentResponseUpdate`, and in terminal/no-content cases there is logic to flush accumulated intermediate updates. Furthermore, `artifact_update` is always yielded so that actual content such as files and binaries is not lost. (Source: [Python _map_a2a_stream main loop](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L565-L666), [Python _updates_from_task loop consumers](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L593-L663))

## .NET hosting

The `.NET` hosting handler splits A2A responses into two kinds.

- If there is no continuation token, a lightweight `Message` response
- If there is a continuation token, surface via **task lifecycle** such as `TaskUpdater.SubmitAsync` / `StartWorkAsync`

On the resumed/update path, an artifact is added upon completion and the task is completed. That is, the hosting layer directly owns the A2A “message vs task” duality. (Source: [.NET A2AAgentHandler HandleNewMessageAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AAgentHandler.cs#L74-L127), [.NET HandleTaskUpdateAsync completion/progress](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AAgentHandler.cs#L160-L213))

## Python hosting

Python `A2AExecutor` projects local agent output onto A2A protocol events.

- A non-streaming final `Message` is a `TaskStatusUpdateEvent`-style working status message
- A streaming `AgentResponseUpdate` becomes a `TaskArtifactUpdateEvent` via `add_artifact(...)`
- Chunks from the same response stream share a **stable artifact id**, and subsequent chunks are given `append=True`
- Intermediate tool-use internal content such as `function_call`/`function_result` is silently skipped and not surfaced as a user-facing A2A part

This last point defines the “tool integration” boundary. That is, the A2A host does not expose the internal tool loop as-is; it transmits only the final text/data/uri output that A2A can understand. (Source: [Python A2AExecutor _run_stream stable artifact id](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_a2a_executor.py#L184-L201), [Python A2AExecutor handle_events mapping](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_a2a_executor.py#L214-L306), [Python test append semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/tests/test_a2a_executor.py#L823-L843), [Python test skipping intermediate tool content](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/tests/test_a2a_executor.py#L861-L876))

## Hosting surface

## .NET hosting

### Registration
`AddA2AServer(...)` registers a keyed `A2AServer` in DI. The default path is as follows.

- keyed `AIAgent` resolve
- optional `IAgentHandler` override resolve
- If absent, creates `AIHostAgent` + `A2AAgentHandler`
- optional `ITaskStore` / `AgentSessionStore` resolve
- If an isolation provider is present, applies a scoped wrapper to both the task store and session store
- Creates `A2AServer`

That is, the .NET hosting package **takes responsibility up to the A2A SDK server object**, and the ASP.NET Core package maps it to an endpoint. (Source: [.NET AddA2AServer overloads](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AServerServiceCollectionExtensions.cs#L49-L178), [.NET CreateA2AServer internals](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AServerServiceCollectionExtensions.cs#L181-L220))

### Endpoint mapping
The ASP.NET layer provides `MapA2AHttpJson` and `MapA2AJsonRpc`. That is, the transport binding is exposed at the route level. (Source: [.NET A2A endpoint mapping](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A.AspNetCore/A2AEndpointRouteBuilderExtensions.cs#L21-L137))

## Python hosting

### Full integration package
Python `A2AExecutor` is a full agent executor implementation; examples combine it with the native A2A SDK's `DefaultRequestHandler`, `InMemoryTaskStore`, and `A2AStarletteApplication`. That is, **A2A protocol app assembly is done by the native SDK**, and the Agent Framework package provides only the executor. (Source: [Python A2A README executor example](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L25-L48))

### Helper-only package
Python `agent-framework-hosting-a2a` does not directly replace the native `AgentExecutor`; it provides only the value conversions and card generation required for an app-owned A2A server. The host continues to own routes, event queue, task store, authentication, and deployment. (Source: [Python hosting-a2a README scope](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/README.md#L3-L10), [same file “surrounding application”](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/hosting-a2a/README.md#L180-L186))

## Host composition responsibilities
In addition to protocol wiring, the A2A host must directly own the following.

- which agent(s) are exposed
- authn/authz
- task store persistence
- task/session identifiers and principal binding
- direct configuration vs curated registry discovery policy
- card publication strategy
- task polling / stream reconnection policy

This is equally required by the Python README's security considerations and the .NET trust model remarks. (Source: [Python A2A README security](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L60-L64), [.NET hosting trust model](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AServerServiceCollectionExtensions.cs#L31-L47))

## .NET

`.NET` `A2AAgentSession` preserves A2A-specific state as a public session type.

- `ContextId`
- `TaskId`

(Source: [.NET A2AAgentSession properties](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgentSession.cs#L22-L69), [.NET UpdateSession consistency check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L341-L360))

- If `session.TaskState == InputRequired`, sets `task_id` directly to continue the same task,
- otherwise, connects follow-up refinement via `reference_task_ids`. (Source: [.NET CreateA2AMessage follow-up rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L362-L385))

## Python

Python still exports `A2AAgentSession` but it is **deprecated**; the preferred path is to place an `A2AServiceSessionId` mapping in a plain `AgentSession.service_session_id`. The session stores the following.

- `context_id`
- `task_id`
- `task_state`

## Concurrency, streaming, and cancellation

## .NET

### Streaming
`A2AAgent.RunStreamingAsync(...)` handles four kinds of payload.

- `Message`
- `Task`
- `StatusUpdate`
- `ArtifactUpdate`

If a continuation token is present, `SubscribeToTask` is used. If `UnsupportedOperation` is received while subscribing to a terminal task, it falls back to `GetTaskAsync`. (Source: [.NET RunCoreStreamingAsync switch](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L163-L234), [.NET subscribe fallback method](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L272-L317))

### Continuation / polling
- Synchronous continuation uses `GetTaskAsync`
- Streaming continuation uses `SubscribeToTask`
- Sending `ContinuationToken` and user messages together is prohibited. (Source: [.NET GetContinuationToken validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgent.cs#L387-L399))

### Hosting-side background policy
`AgentRunMode` determines whether the hosted A2A server surfaces responses as messages or as tasks. (Source: [.NET AgentRunMode](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/AgentRunMode.cs#L31-L84))

## Python

### Streaming
Python `A2AAgent.run(..., stream=True)` returns a `ResponseStream`, and if `continuation_token` is present, it resubscribes via `SubscribeToTaskRequest`. If background=False, it internally waits until task completion; if background=True, it surfaces the continuation token of the in-progress task. (Source: [Python A2AAgent.run overloads and docs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L419-L473), [continuation_token subscribe path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L483-L520))

### Polling
Python separately provides `poll_task(continuation_token)`. Unlike the SSE resubscribe of `run(continuation_token=...)`, this is **single request polling**. (Source: [Python poll_task](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L850-L869))

### Hosting executor streaming
`A2AExecutor` reuses the stable artifact id for each streaming update and gives subsequent chunks `append=True`, allowing clients to coalesce them into a single artifact/message. (Source: [Python A2AExecutor _run_stream](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_a2a_executor.py#L184-L201), [Python test append=True for subsequent chunk](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/tests/test_a2a_executor.py#L823-L843))

### Cancellation
- In the Python hosting executor, `cancel()` calls `TaskUpdater.cancel()`.
- `execute()` catches `CancelledError` and changes the task state to `CANCELED`. (Source: [Python A2AExecutor.cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_a2a_executor.py#L116-L139), [Python execute cancel/fail path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_a2a_executor.py#L140-L183))

(Source: [.NET A2AAgentHandler.CancelAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AAgentHandler.cs#L67-L72))

## Identity boundaries and security

A2A's `contextId`, `taskId`, and session/thread identifiers are strictly **routing handles**. Both languages state that these values must not be treated as bearer credentials.

- .NET hosting explicitly states that claims-based isolation or a custom `AgentIsolationKeyProvider` should be used in a multi-user host.
- The Python README also warns not to rely solely on client-supplied identifiers before binding to an authenticated user/tenant/workspace. (Source: [.NET hosting trust model](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Hosting.A2A/A2AServerServiceCollectionExtensions.cs#L31-L47), [Python A2A security considerations](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/README.md#L60-L64))

## Java decisions

## Module separation proposal

### 1. `agent-framework-a2a`
- Java surface that wraps a remote A2A client as an `AIAgent`
- Provides both `AgentCard`-based bootstrap and direct configured client bootstrap
- Stores `A2AServiceSessionId` or equivalent structured session state in `AgentSession.serviceSessionId`

### 2. `agent-framework-hosting-a2a`
- Conversion helpers and card adapters for use by an app-owned native A2A server
- `a2aToRun`, `a2aFromRun`, `agentCardAdapter`, `workflowCardAdapter`
- The host determines the task/artifact/message grouping policy

### 3. `agent-framework-hosting-a2a-spring`
- Spring MVC/WebFlux route binder
- auth filter, principal-derived isolation key, SSE/JSON-RPC wiring
- Separated from the generic hosting core

## Policy decisions
- The default public design is better kept **app-owned native A2A composition-friendly**, like the Python helper.
- However, the remote A2A client wrapper (`A2AAgent`) is a core feature present in both .NET and Python, so it should be provided as a first-class surface.
- Recommending structured `service_session_id` mapping as in Python for session state, and keeping the `.NET`-style separate session subclass only as an optional compatibility layer, is the more forward-looking approach. (Source: [Python A2AServiceSessionId preference](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/a2a/agent_framework_a2a/_agent.py#L59-L80), [.NET A2AAgentSession dedicated type](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.A2A/A2AAgentSession.cs#L12-L69))

## Acceptance scenarios

1. **Remote agent as local agent**
   - It must be possible to invoke a remote agent like an `AIAgent` via a direct-configured A2A client or a discovered `AgentCard`.
   - If the response is an immediate message, it must be converted to an assistant message; if it is a task, it must be converted to a task-derived response/continuation token.

2. **Task continuation**
   - An in-progress task must surface a continuation token.
   - If terminal task resubscription is unsupported, a fallback polling path must exist.
   - When using a continuation token, new user messages received simultaneously must be rejected.

3. **Message/task linking**
   - If the session points to an `INPUT_REQUIRED` task state, the outbound A2A message must continue the same task via `task_id`.
   - Otherwise, follow-up refinement must be expressed via `reference_task_ids`.

4. **Cards**
   - An app-owned A2A host must be able to generate and publish a public `AgentCard`.
   - Supported interfaces, capabilities, modes, and skills must be explicitly adjustable.

5. **Artifacts**
   - A streaming host must group chunks of the same logical response under the same artifact id and provide append semantics.
   - file/data/uri outputs must be delivered without loss as artifact/message updates.

6. **Identity boundary**
   - `contextId`, `taskId`, and session/thread ids must be routing handles, not bearer credentials.
   - A multi-user host must separately compose the principal/tenant dimension.

7. **Tool integration boundary**
   - The host must not send internal tool-use intermediate frames directly over the A2A wire; it must surface only the final user-facing output that A2A can understand.

## Conclusion

In this repository, A2A is implemented not merely as “one more external chat protocol” but as a **task-bearing agent protocol**. In remote agent integration, tasks/continuations and artifacts are central; in hosting integration, the key questions are when and by what criteria to surface messages and task lifecycles, and how to connect those identifiers to principal-scoped state. The Java implementation is most naturally structured to follow this same layout by separating the **remote A2A agent wrapper**, **A2A hosting helper**, and **framework-specific binder**, and by keeping the card/stream/task/artifact model as first-class concepts.
