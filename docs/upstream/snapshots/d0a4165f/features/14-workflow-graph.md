## 목적·경계

### 목적

- 이 기능의 핵심 목적은 **(1) 실행 가능한 워크플로 그래프를 정의하고**, **(2) 각 executor의 메시지 처리 규약을 타입 수준에서 기술하며**, **(3) 그래프의 edge를 따라 메시지를 안전하게 전달하는 것**이다. .NET은 builder가 executor binding, edge, output designation, request port를 수집한 뒤 `Workflow`를 만들고, Python도 같은 역할을 하는 builder가 edge groups, executors, checkpoint storage, output designation을 모아 `Workflow`를 만든다. ([.NET WorkflowBuilder fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L30-L41), [.NET Build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L616-L680), [Python WorkflowBuilder init](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L91-L170), [Python build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L891))

### 경계

- 이 문서는 **그래프 정의와 검증, executor 프로토콜, edge 라우팅**을 직접 다루는 구현까지만 포함한다. 실제 세션 저장, orchestration 패턴별 conversation 정책, declarative YAML lowering, hosted agent transport는 별도 기능 문서의 범위다. 코드상으로도 이 문서의 직접 대상은 `.NET`의 `WorkflowBuilder`/`Executor`/`Edge`/`Execution/*`과 Python의 `_workflow_builder.py`/`_executor.py`/`_edge.py`/`_edge_runner.py`에 집중되어 있다. ## 상세 실행 흐름

### 1. 그래프 정의와 빌드

- .NET builder는 내부적으로 executor bindings, outgoing edges, request ports, output executor tags를 수집한다. `Track(...)`는 placeholder/unbound executor를 따로 기억하고, concrete binding이 들어오면 type과 instance 일관성을 검사한다. ([Builder state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L30-L41), [Track logic](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L52-L97))
- .NET에서 direct edge는 `AddEdge(...)`, fan-out은 `AddFanOutEdge(...)`, fan-in barrier는 `AddFanInBarrierEdge(...)`로 추가된다. direct edge는 optional predicate와 label을 받을 수 있고, fan-out은 target selector를, fan-in은 source 모두가 메시지를 낼 때까지 hold하는 barrier semantics를 가진다. ([AddEdge](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L245-L395), [AddFanOutEdge](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L397-L489), [AddFanInBarrierEdge](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L491-L536))
- Python builder는 `_edge_groups`와 `_executors`를 중심으로 그래프를 구성한다. direct edge, fan-out, switch-case, multi-selection, fan-in, chain을 모두 fluent API로 추가하고, 최종 `build()`가 validator를 호출한 뒤 `Workflow`를 만든다. ([Builder storage](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L147-L170), [add_edge/add_fan_out](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L230-L336), [switch-case/multi-selection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L338-L509), [fan-in/chain](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L511-L618), [build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L891))
- Python `Workflow`는 build 직후 graph signature와 hash를 계산해 topology fingerprint를 만든다. 이 값은 checkpoint compatibility의 기준이 된다. ([graph signature fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L330-L347), [signature computation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1096-L1161))

### 2. Executor 프로토콜과 타입 시스템

- .NET의 `Executor`는 `ConfigureProtocol(ProtocolBuilder)`를 override하는 방식으로 입력 route, `SendsMessage`, `YieldsOutput`를 선언한다. runtime은 `ExecutorProtocol`을 lazy하게 구성하고 `DescribeProtocol()`, `InputTypes`, `OutputTypes`, `CanHandle()`로 introspection을 제공한다. ([Executor protocol setup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L195-L216), [Executor introspection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L349-L372))
- .NET의 generic executor base (`Executor<TInput>`, `Executor<TInput,TOutput>`)는 `HandleAsync(...)`를 직접 route builder에 등록한다. 즉 단일-input handler executor를 만들 때 가장 얇은 공개 기본 클래스다. ([Executor<TInput>](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L375-L397), [Executor<TInput,TOutput>](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L399-L422))
- .NET runtime에서 actual handler invocation은 `ExecuteCoreAsync(...)`가 담당한다. 이 메서드는 `ExecutorInvokedEvent`를 추가하고, `Router.RouteMessageAsync(...)`로 handler를 찾은 뒤, success면 `ExecutorCompletedEvent`, failure면 `ExecutorFailedEvent`를 추가한다. non-void result는 옵션에 따라 downstream message와 workflow output으로 자동 승격된다. ([ExecuteCoreAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L257-L310))
- Python의 `Executor`는 `@handler` metadata를 class introspection으로 발견해 `_handlers`와 `_handler_specs`를 구성한다. handler의 input type과 `WorkflowContext[T,U]` generic parameter가 output types와 workflow output types를 결정한다. ([handler discovery](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L357-L381), [output type API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L438-L477), [handler decorator contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L575-L737))
- Python handler signature validation은 두 경로를 갖는다. 기본은 annotations introspection이고, explicit mode는 `@handler(input=..., output=..., workflow_output=...)`다. unresolved `TypeVar`, duplicate handlers, invalid `WorkflowContext` annotation은 모두 registration 시점에 실패한다. ([explicit vs introspection handler mode](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L590-L707), [signature validator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L745-L811))
- Python executor 실행은 항상 per-executor `asyncio.Lock` 아래에서 직렬화된다. 그래서 같은 superstep 안에 여러 source가 동일 target executor로 메시지를 보내도 그 executor의 실제 handler body는 한 번에 하나씩만 수행된다. ### 3. Edge 그룹과 라우팅 실행

- .NET의 `Edge`는 `EdgeKind`와 concrete `EdgeData`의 tagged union이다. concrete runtime shape는 `DirectEdgeData`, `FanOutEdgeData`, `FanInEdgeData`뿐이다. direct edge는 source/sink/optional predicate를, fan-out은 ordered sink list와 optional assigner를, fan-in은 ordered source list와 single sink를 가진다. ([Edge union](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Edge.cs#L27-L76), [DirectEdgeData](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/DirectEdgeData.cs#L8-L40), [FanOutEdgeData](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/FanOutEdgeData.cs#L10-L42), [FanInEdgeData](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/FanInEdgeData.cs#L8-L31))
- .NET `DirectEdgeRunner`는 target mismatch, condition false, type mismatch를 구분해 drop하고, deliverable인 경우에만 `DeliveryMapping`을 만든다. `FanOutEdgeRunner`는 selector 결과를 target IDs로 바꾼 뒤 각 target executor의 `CanHandle`을 확인해 병렬 전달 대상을 결정한다. `FanInEdgeRunner`는 source별 버퍼를 유지하다가 모두 준비되면 aggregated delivery로 sink를 한 번 호출한다. ([DirectEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/DirectEdgeRunner.cs#L13-L54), [FanOutEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanOutEdgeRunner.cs#L15-L68), [FanInEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanInEdgeRunner.cs#L19-L115))
- Python도 같은 개념을 `Edge` + `EdgeGroup` 계층으로 구현한다. `Edge`는 optional condition을 가지며, `FanOutEdgeGroup`은 optional `selection_func`, `FanInEdgeGroup`은 여러 source의 병합, `SwitchCaseEdgeGroup`은 ordered case/default single-dispatch를 담당한다. ([Edge predicate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L169-L198), [FanOutEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L499-L611), [FanInEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L614-L646), [SwitchCaseEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L806-L944))
- Python runtime의 `SingleEdgeRunner`, `FanOutEdgeRunner`, `FanInEdgeRunner`는 .NET과 유사한 책임 분해를 갖지만, **동일 edge runner를 통과하는 메시지 순서 보존**을 더 직접적으로 구현한다. `RunnerImpl._run_iteration()`은 source마다 연결된 edge runner들을 병렬로 돌리되, 각 edge runner 내부에서는 source messages를 순서대로 흘린다. ([Runner ordering comment](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L179-L229), [SingleEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L91-L160), [FanOutEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L163-L295), [FanInEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L297-L429))

### 4. Graph validation

- .NET build validation은 먼저 **unbound executor**를 금지하고, 그다음 start executor로부터 도달할 수 없는 executor가 있으면 **unreachable executor**로 실패시킨다. direct/fan-out/fan-in edges는 모두 reachability walk에 반영된다. ([.NET validate unbound/unreachable](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L543-L613))
- .NET은 **source → target 메시지 타입 호환성을 build 시점에 완전하게 검증하지 못한다**는 점을 코드 주석으로 명시한다. 이유는 executor가 async factory로 생성될 수 있고, handler registration이 runtime에 일어나며, conditional routing과 future fan-in strategy가 타입 추론을 어렵게 만들기 때문이다. 즉 .NET graph validation은 reachability와 binding 완전성에는 강하지만, 모든 type-flow soundness를 compile-time에 보장하지는 않는다. ([.NET validation limitation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L588-L604))
- Python build는 explicit output designation 자체를 먼저 검증한다. explicit mode에서 output/intermediate가 둘 다 비면 실패하고, duplicate outputs, duplicate intermediates, overlap은 모두 build-time 오류다. ([designation validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L686-L725))
- Python builder는 그 다음 `validate_workflow_graph(...)`를 호출한 후에만 `Workflow`를 만든다. source 주석은 이 validator가 start executor 존재, edge validity, graph connectivity, type compatibility를 검증 대상으로 둔다고 설명한다. ([Python build docstring](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L742), [Python validator call](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L843-L850))
- 테스트 관점에서도 .NET은 unbound executor, unreachable executor, duplicate rebind mismatch를 즉시 거부하고, Python은 duplicate agent-derived executor id와 invalid designation 설정을 거부한다. ([.NET builder tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L25-L68), [.NET rebind mismatch test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L99-L129), [Python duplicate id test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L159-L167))

## 상태·영속화

### 정의 상태와 정의 스냅샷

- .NET builder는 build 전까지 executor bindings, edges, ports, output tags를 mutable하게 유지하고, `Build()` 후에는 이 사전들이 `Workflow` 인스턴스의 정의 스냅샷이 된다. `Workflow.ReflectExecutors()`, `ReflectEdges()`, `ReflectPorts()`는 이 스냅샷을 복사해 노출한다. ([Builder mutable definition state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L30-L41), [Workflow reflection API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Workflow.cs#L33-L67))
- Python `Workflow.to_dict()`는 `edge_groups`, `executors`, `start_executor_id`, output/intermediate executor ids를 JSON-ready dictionary로 내보내며, nested `WorkflowExecutor`가 있으면 child workflow definition도 함께 직렬화한다. ([Workflow.to_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L386-L420))

### 실행 상태와 snapshot compatibility

- Python은 build 결과에 `graph_signature`와 `graph_signature_hash`를 저장하고, checkpoint restore 시 이 hash가 바뀌면 restore를 거부한다. 그래서 “같은 이름의 workflow”가 아니라 “동일 topology의 workflow”가 compatibility 기준이다. ([signature fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L330-L347), [signature computation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1096-L1161))
- .NET은 graph core 자체보다 runtime checkpoint 경로에서 정의 스냅샷을 활용한다. `InProcessRunner.RestoreCheckpointCoreAsync()`는 checkpoint의 workflow signature가 현재 workflow와 맞지 않으면 `InvalidDataException`을 던진다. ([restore compatibility check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L404-L412))

### edge state

- .NET에서 stateful edge는 fan-in runner다. `FanInEdgeRunner`는 내부 `_state`를 `PortableValue`로 export/import하여 checkpoint에 포함시킨다. ([FanIn state export/import](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanInEdgeRunner.cs#L98-L115))
- Python에서 edge definition은 직렬화되지만 live callable은 저장되지 않는다. `Edge.from_dict()`와 `EdgeGroup.from_dict()`는 callable 대신 이름만 보존하고, 복원 시 `_missing_callable(...)` placeholder를 설치한다. 따라서 직렬화/복원은 **정의 보존**이지 **callable 실행 복원**이 아니다. ([Edge serialization](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L200-L241), [EdgeGroup.from_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L421-L465), [missing callable placeholder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L50-L72))

## 동시성·스트리밍·취소

- .NET은 workflow-level concurrent reuse를 **모든 executor binding이 concurrent shared execution을 지원할 때만** 허용한다. 그렇지 않으면 동일 workflow 인스턴스의 concurrent run을 막는다. ([Workflow.AllowConcurrent](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Workflow.cs#L89-L93), [InProcessRunner concurrent-run gate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L45-L52))
- Python은 같은 `Workflow` 인스턴스에 대한 동시 실행을 `self._active_run` weakref로 막는다. run이 active인 동안 새 `run()`은 즉시 `WorkflowException`을 던진다. ([active run state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L367-L384), [concurrency guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L791))
- Python executor는 per-executor lock으로 handler body를 직렬화하지만, runner는 서로 다른 edge runners는 병렬로 돌린다. 즉 “동일 target executor의 실제 실행은 직렬”, “서로 다른 routing path는 병렬”이라는 계층 분리가 있다. ([executor lock](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L202-L244), [runner parallel edge delivery](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L201-L229))
- 스트리밍은 graph layer에서 별도 edge 타입으로 구현되지 않는다. 대신 executor가 `yield_output(...)` 또는 non-void result를 내면 event stream이 이를 실시간으로 surface한다. .NET은 handler result object를 자동 send/auto-yield할 수 있고, Python은 `WorkflowContext.yield_output()`가 executor designation에 따라 `output` 또는 `intermediate`로 분류한다. ([.NET auto-send/auto-yield](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L300-L307), [Python yield_output classifier](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L350-L380))
- 취소는 graph definition이 아니라 runtime이 담당한다. .NET 쪽 graph/executor layer는 `CancellationToken`을 핸들러와 route overload 전반에 전달하고, edge runners도 이를 받는다. Python core에서는 explicit graph-definition-level cancel API는 보이지 않고, runner가 `asyncio.CancelledError`를 iteration task로 propagate하는 방식이다. ([.NET generic executor cancellation signature](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L396-L422), [.NET RouteBuilder tests with cancellation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/RouteBuilderTests.cs#L68-L128), [Python runner cancellation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142))

## 오류·검증·보안

- .NET builder는 같은 id에 대해 다른 executor type 또는 다른 instance를 rebind하려 하면 실패한다. 이 검사는 executor identity drift를 build 시점에 막는다. ([rebind checks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L63-L77))
- .NET builder는 동일 source-target unconditional edge 중복도 거부한다. `idempotent=true`일 때만 no-op로 바뀐다. ([duplicate unconditional edge check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L377-L388))
- .NET shared-state tests는 fan-out된 두 executor가 같은 shared key를 쓰는 경우 runtime error를 기대한다. 즉 graph layer 자체는 fan-out을 허용하지만, state model은 multi-writer 충돌을 실패로 surface할 수 있다. ([InProcessStateTests conflict case](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessStateTests.cs#L145-L181))
- Python builder는 explicit output designation이 비어 있거나 중복되거나 overlap되면 build-time에 바로 실패한다. 이는 event surface ambiguity를 사전에 차단하는 validation이다. ([designation validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L686-L725))

## 문서 차이

- 이 기능 범위에서 별도 README보다 **소스 주석과 테스트가 더 구체적**이다. 특히 .NET은 `WorkflowBuilder.Validate()` 안에서 “왜 build 시점에 완전한 타입 호환 검증을 못 하는지”를 코드 주석으로 명시하지만, public builder surface만 봐서는 이 한계가 바로 드러나지 않는다. 코드 우선으로 보면, .NET graph validation은 reachability와 binding 완전성에 더 강하고 type-flow soundness는 일부 runtime까지 미뤄진다. ([.NET validation limitation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L588-L604))
- .NET은 legacy `IMessageHandler<>`/`YieldsMessageAttribute`가 여전히 소스에 남아 있지만, 실제 코드는 이를 obsolete로 처리하고 generator 기반 partial-class 경로를 우선 경로로 둔다. 따라서 문서화된 “가능한 방법”보다 코드가 정의하는 “권장/실제 경로”가 더 좁다. ([IMessageHandler obsolete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Reflection/IMessageHandler.cs#L13-L18), [YieldsMessage obsolete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/ObsoleteAttributes.cs#L8-L32), [Generator pipeline](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/ExecutorRouteGenerator.cs#L29-L75))
- Python 쪽은 builder docstring이 type compatibility까지 validator가 본다고 설명하고 실제로 `validate_workflow_graph(...)`를 호출하지만, 이 문서 작성 시 validator 내부 파일은 직접 읽지 않았다. 따라서 Python의 “어떤 규칙까지 compile-time에 검사하는지”는 이 문서에서 **validator 호출과 테스트가 보여 주는 범위까지만** 확정적으로 기술한다. ([Python build docstring](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L742), [Python validator call](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L843-L850))

## Java 결정

- Java 구현은 **그래프 정의 객체**와 **실행 런타임**을 분리한다. builder는 immutable한 graph definition을 만들고, runtime은 그 definition을 받아 run handle을 생성하는 2단 구조가 적합하다. Python의 `graph_signature_hash`와 .NET의 restore compatibility gate를 보면, graph definition이 독립된 identity를 갖는 편이 checkpoint/resume에 유리하다. ([Python graph signature](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L330-L347), [.NET restore compatibility](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L404-L412))
- Java edge model은 `.NET`처럼 runtime edge kind를 `DIRECT`, `FAN_OUT`, `FAN_IN`으로 좁게 두고, Python처럼 high-level switch/multi-selection DSL은 builder lowering으로 처리하는 방식을 권장한다. 이렇게 하면 runtime state와 observability가 단순해진다. ([.NET EdgeKind](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Edge.cs#L11-L25), [.NET SwitchBuilder lowering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SwitchBuilder.cs#L91-L96), [Python SwitchCaseEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L806-L944))
- Java executor API는 `.NET`의 compile-time generator 장점과 Python의 간단한 annotation model을 절충해, **annotation processor 기반 route registration**을 우선 경로로 두는 것이 좋다. runtime reflection-only 모델보다 cold start와 validation 품질이 좋아진다. ([.NET Generator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/ExecutorRouteGenerator.cs#L29-L75), [Generated source builder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/Generation/SourceBuilder.cs#L71-L247))
- Java는 serialized edge callable을 절대 자동 복원하지 말고, Python처럼 **symbolic name + explicit registry rebinding**만 허용해야 한다. 복원 불가능한 callable은 fail-closed로 에러를 내는 편이 안전하다. ([Python missing callable](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L50-L72), [Python Edge.from_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L219-L241))
- Java 동시성 모델은 Python처럼 per-executor serialization lock을 기본으로 두고, edge-runner 단위 병렬성을 허용하는 구조가 안전하다. 이 방식은 multi-source same-target races를 줄이면서 fan-out parallelism은 유지한다. ([Python executor lock](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L202-L244), [Python runner edge parallelism](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L201-L229))

## 구체 acceptance scenarios

1. **unbound executor가 남아 있으면 build가 실패해야 한다.** .NET은 placeholder/unbound executor를 별도로 추적하고 `Build()`에서 거부하며, test가 이를 고정한다. ([.NET unbound validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L543-L551), [.NET test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L25-L36))

([.NET reachability validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L553-L613), [.NET unreachable test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L39-L49))

3. **동일 agent 인스턴스를 여러 edge에 재사용하면 Python builder는 같은 wrapper를 재사용해야 한다.** test는 동일 agent를 세 번 사용해도 `AgentExecutor` wrapper 수가 중복되지 않음을 검증한다.
