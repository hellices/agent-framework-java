## Purpose and boundary

### Purpose

- The core purpose of this feature is **(1) to define an executable workflow graph**, **(2) to describe each executor's message handling contract at the type level**, and **(3) to deliver messages safely along the edges of the graph**. In .NET the builder collects the executor bindings, edges, output designations, and request ports and then creates a `Workflow`; in Python a builder playing the same role collects the edge groups, executors, checkpoint storage, and output designations and creates a `Workflow`. ([.NET WorkflowBuilder fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L30-L41), [.NET Build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L616-L680), [Python WorkflowBuilder init](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L91-L170), [Python build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L891))

## Detailed execution flow

### 1. Graph definition and build

- The .NET builder internally collects executor bindings, outgoing edges, request ports, and output executor tags. `Track(...)` remembers placeholder/unbound executors separately, and checks type and instance consistency once a concrete binding arrives. ([Builder state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L30-L41), [Track logic](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L52-L97))
- In .NET a direct edge is added with `AddEdge(...)`, a fan-out with `AddFanOutEdge(...)`, and a fan-in barrier with `AddFanInBarrierEdge(...)`. A direct edge can take an optional predicate and a label, a fan-out takes a target selector, and a fan-in has barrier semantics that hold until every source has emitted a message. ([AddEdge](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L245-L395), [AddFanOutEdge](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L397-L489), [AddFanInBarrierEdge](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L491-L536))
- The Python builder composes the graph around `_edge_groups` and `_executors`. Direct edges, fan-out, switch-case, multi-selection, fan-in, and chain are all added through the fluent API, and the final `build()` calls the validator and then creates the `Workflow`. ([Builder storage](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L147-L170), [add_edge/add_fan_out](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L230-L336), [switch-case/multi-selection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L338-L509), [fan-in/chain](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L511-L618), [build](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L891))
- The Python `Workflow` computes the graph signature and hash right after the build to make a topology fingerprint. That value is the criterion for checkpoint compatibility. ([graph signature fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L330-L347), [signature computation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1096-L1161))

### 2. The executor protocol and the type system

- The .NET `Executor` declares the input routes, `SendsMessage`, and `YieldsOutput` by overriding `ConfigureProtocol(ProtocolBuilder)`. The runtime lazily composes the `ExecutorProtocol` and provides introspection through `DescribeProtocol()`, `InputTypes`, `OutputTypes`, and `CanHandle()`. ([Executor protocol setup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L195-L216), [Executor introspection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L349-L372))
- The .NET generic executor bases (`Executor<TInput>`, `Executor<TInput,TOutput>`) register `HandleAsync(...)` directly with the route builder. They are therefore the thinnest public base class for making a single-input handler executor. ([Executor<TInput>](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L375-L397), [Executor<TInput,TOutput>](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L399-L422))
- In the .NET runtime the actual handler invocation is handled by `ExecuteCoreAsync(...)`. That method adds an `ExecutorInvokedEvent`, finds the handler with `Router.RouteMessageAsync(...)`, and then adds an `ExecutorCompletedEvent` on success or an `ExecutorFailedEvent` on failure. A non-void result is automatically promoted to a downstream message and a workflow output depending on the options. ([ExecuteCoreAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L257-L310))
- The Python `Executor` discovers `@handler` metadata through class introspection to compose `_handlers` and `_handler_specs`. The handler's input type and the `WorkflowContext[T,U]` generic parameters determine the output types and the workflow output types. ([handler discovery](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L357-L381), [output type API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L438-L477), [handler decorator contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L575-L737))
- Python handler signature validation has two paths. The default is annotations introspection, and the explicit mode is `@handler(input=..., output=..., workflow_output=...)`. An unresolved `TypeVar`, duplicate handlers, and an invalid `WorkflowContext` annotation all fail at registration time. ([explicit vs introspection handler mode](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L590-L707), [signature validator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L745-L811))
- Python executor execution is always serialized under a per-executor `asyncio.Lock`. Even when several sources send messages to the same target executor within one superstep, that executor's actual handler body therefore runs only one at a time. ([execution lock](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L202-L244), [execute()](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L246-L323))
- .NET also supports a compile-time generator path. `ExecutorRouteGenerator` gathers the methods carrying `[MessageHandler]` and the classes carrying `[SendsMessage]`/`[YieldsOutput]` to generate partial `ConfigureProtocol`/`ConfigureRoutes` code, and `SourceBuilder` turns the actual `.SendsMessage<T>()`, `.YieldsOutput<T>()`, and `.ConfigureRoutes(...)` chain into emitted source. ([ExecutorRouteGenerator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/ExecutorRouteGenerator.cs#L16-L87), [SourceBuilder generated protocol](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/Generation/SourceBuilder.cs#L71-L107), [SourceBuilder generated routes](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/Generation/SourceBuilder.cs#L129-L247))

### 3. Edge groups and routing execution

- The .NET `Edge` is a tagged union of `EdgeKind` and a concrete `EdgeData`. The only concrete runtime shapes are `DirectEdgeData`, `FanOutEdgeData`, and `FanInEdgeData`. A direct edge has a source/sink/optional predicate, a fan-out has an ordered sink list and an optional assigner, and a fan-in has an ordered source list and a single sink. ([Edge union](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Edge.cs#L27-L76), [DirectEdgeData](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/DirectEdgeData.cs#L8-L40), [FanOutEdgeData](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/FanOutEdgeData.cs#L10-L42), [FanInEdgeData](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/FanInEdgeData.cs#L8-L31))
- The .NET `DirectEdgeRunner` distinguishes a target mismatch, a false condition, and a type mismatch when dropping, and builds a `DeliveryMapping` only when the message is deliverable. `FanOutEdgeRunner` turns the selector result into target IDs and then checks each target executor's `CanHandle` to decide the parallel delivery targets. `FanInEdgeRunner` keeps a per-source buffer and calls the sink once with an aggregated delivery when all of them are ready. ([DirectEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/DirectEdgeRunner.cs#L13-L54), [FanOutEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanOutEdgeRunner.cs#L15-L68), [FanInEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanInEdgeRunner.cs#L19-L115))
- Python implements the same concepts with an `Edge` plus `EdgeGroup` layering. An `Edge` has an optional condition, `FanOutEdgeGroup` has an optional `selection_func`, `FanInEdgeGroup` merges several sources, and `SwitchCaseEdgeGroup` handles ordered case/default single dispatch. ([Edge predicate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L169-L198), [FanOutEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L499-L611), [FanInEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L614-L646), [SwitchCaseEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L806-L944))

([Runner ordering comment](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L179-L229), [SingleEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L91-L160), [FanOutEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L163-L295), [FanInEdgeRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L297-L429))

### 4. Graph validation

- .NET build validation first forbids an **unbound executor**, and then fails with an **unreachable executor** when an executor cannot be reached from the start executor. Direct/fan-out/fan-in edges are all reflected in the reachability walk. ([.NET validate unbound/unreachable](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L543-L613))
- .NET states in a code comment that **it cannot completely validate source → target message type compatibility at build time**. The reasons are that an executor can be created by an async factory, that handler registration happens at runtime, and that conditional routing and a future fan-in strategy make type inference hard. .NET graph validation is therefore strong on reachability and binding completeness but does not guarantee all type-flow soundness at compile time. ([.NET validation limitation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L588-L604))
- The Python build validates the explicit output designation itself first. In explicit mode it fails when both output and intermediate are empty, and duplicate outputs, duplicate intermediates, and overlap are all build-time errors. ([designation validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L686-L725))
- The Python builder then creates the `Workflow` only after calling `validate_workflow_graph(...)`. The source comment explains that this validator takes the existence of the start executor, edge validity, graph connectivity, and type compatibility as its validation subjects. ([Python build docstring](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L742), [Python validator call](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L843-L850))
- From the test perspective too, .NET immediately rejects an unbound executor, an unreachable executor, and a duplicate rebind mismatch, while Python rejects duplicate agent-derived executor ids and an invalid designation configuration. ([.NET builder tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L25-L68), [.NET rebind mismatch test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L99-L129), [Python duplicate id test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L159-L167))

## State and persistence

### Definition state and the definition snapshot

- The .NET builder keeps the executor bindings, edges, ports, and output tags mutable until the build, and after `Build()` those dictionaries become the definition snapshot of the `Workflow` instance. `Workflow.ReflectExecutors()`, `ReflectEdges()`, and `ReflectPorts()` copy and expose that snapshot. ([Builder mutable definition state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L30-L41), [Workflow reflection API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Workflow.cs#L33-L67))
- The Python `Workflow.to_dict()` emits `edge_groups`, `executors`, `start_executor_id`, and the output/intermediate executor ids as a JSON-ready dictionary, and when there is a nested `WorkflowExecutor` it serializes the child workflow definition along with it. ([Workflow.to_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L386-L420))

### Execution state and snapshot compatibility

- Python stores `graph_signature` and `graph_signature_hash` in the build result and refuses a restore when that hash has changed at checkpoint restore time. The compatibility criterion is therefore “a workflow with the same topology” rather than “a workflow with the same name”. ([signature fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L330-L347), [signature computation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1096-L1161))
- .NET uses the definition snapshot on the runtime checkpoint path rather than in the graph core itself. `InProcessRunner.RestoreCheckpointCoreAsync()` throws an `InvalidDataException` when the checkpoint's workflow signature does not match the current workflow. ([restore compatibility check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L404-L412))

### edge state

- In .NET the stateful edge is the fan-in runner. `FanInEdgeRunner` exports/imports its internal `_state` as a `PortableValue` to include it in the checkpoint. ([FanIn state export/import](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanInEdgeRunner.cs#L98-L115))
- In Python the edge definition is serialized but the live callable is not stored. `Edge.from_dict()` and `EdgeGroup.from_dict()` preserve only the name instead of the callable, and install a `_missing_callable(...)` placeholder on restore. Serialization/restore is therefore **definition preservation**, not **callable execution restoration**. ([Edge serialization](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L200-L241), [EdgeGroup.from_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L421-L465), [missing callable placeholder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L50-L72))

## Concurrency, streaming, and cancellation

- .NET allows workflow-level concurrent reuse **only when every executor binding supports concurrent shared execution**. Otherwise it blocks concurrent runs of the same workflow instance. ([Workflow.AllowConcurrent](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Workflow.cs#L89-L93), [InProcessRunner concurrent-run gate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L45-L52))
- Python blocks concurrent execution of the same `Workflow` instance with a `self._active_run` weakref. While a run is active, a new `run()` immediately throws a `WorkflowException`. ([active run state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L367-L384), [concurrency guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L791))
- A Python executor serializes the handler body with a per-executor lock, but the runner runs different edge runners in parallel. There is therefore a layered separation of “the actual execution of the same target executor is serial” and “different routing paths are parallel”. ([executor lock](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L202-L244), [runner parallel edge delivery](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L201-L229))
- Streaming is not implemented as a separate edge type at the graph layer. Instead, when an executor emits `yield_output(...)` or a non-void result, the event stream surfaces it in real time. .NET can auto-send/auto-yield the handler result object, and Python's `WorkflowContext.yield_output()` classifies it as `output` or `intermediate` depending on the executor designation. ([.NET auto-send/auto-yield](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L300-L307), [Python yield_output classifier](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L350-L380))
- Cancellation is handled by the runtime rather than by the graph definition. The .NET graph/executor layer passes the `CancellationToken` through the handlers and all route overloads, and the edge runners receive it too. In the Python core no explicit graph-definition-level cancel API is visible, and the runner propagates `asyncio.CancelledError` to the iteration task instead. ([.NET generic executor cancellation signature](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Executor.cs#L396-L422), [.NET RouteBuilder tests with cancellation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/RouteBuilderTests.cs#L68-L128), [Python runner cancellation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142))

## Errors, validation, and security

- The .NET builder fails when a rebind to the same id is attempted with a different executor type or a different instance. This check blocks executor identity drift at build time. ([rebind checks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L63-L77))
- The .NET builder also rejects a duplicate unconditional edge for the same source-target pair. It becomes a no-op only when `idempotent=true`. ([duplicate unconditional edge check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L377-L388))
- The .NET shared-state tests expect a runtime error when two fanned-out executors use the same shared key. The graph layer itself allows fan-out, but the state model can surface a multi-writer conflict as a failure. ([InProcessStateTests conflict case](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessStateTests.cs#L145-L181))
- The Python builder fails immediately at build time when the explicit output designation is empty, duplicated, or overlapping. This is validation that blocks event surface ambiguity in advance. ([designation validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L686-L725))
- A Python serialized edge does not restore the callable automatically. It keeps only the name and installs a placeholder that throws a `RuntimeError` when it is called after restore. This approach avoids the silent corruption of “quietly performing different routing” and makes a missing registration fail closed. ([missing callable](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L50-L72), [Edge.from_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L219-L241), [SwitchCase placeholder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L696-L722))
- The Python executor layer also blocks lifecycle event spoofing. When an executor tries to emit `type='output'`, `type='intermediate'`, or a lifecycle event directly, it is replaced with a warning event and the original event is ignored. This is a defense on the integrity of the graph-level event channel. ([reserved event spoofing guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L382-L401))

## Documentation differences

- Within this feature scope the **source comments and the tests are more concrete** than any separate README. In .NET in particular, the comment inside `WorkflowBuilder.Validate()` states explicitly “why complete type compatibility validation cannot be done at build time”, but that limit is not immediately visible from the public builder surface alone. Code first, .NET graph validation is stronger on reachability and binding completeness, and some of the type-flow soundness is deferred to the runtime. ([.NET validation limitation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L588-L604))
- The .NET legacy `IMessageHandler<>`/`YieldsMessageAttribute` still remain in the source, but the actual code marks them obsolete and puts the generator-based partial-class path first. The “recommended/actual path” the code defines is therefore narrower than the “possible ways” that are documented. ([IMessageHandler obsolete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Reflection/IMessageHandler.cs#L13-L18), [YieldsMessage obsolete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/ObsoleteAttributes.cs#L8-L32), [Generator pipeline](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/ExecutorRouteGenerator.cs#L29-L75))
- On the Python side the builder docstring explains that the validator also looks at type compatibility, and it does call `validate_workflow_graph(...)`, but the validator's internal file was not read directly while writing this document. What rules Python checks at compile time is therefore described here definitively **only as far as the validator call and the tests show**. ([Python build docstring](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L727-L742), [Python validator call](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L843-L850))

## Java decisions

- The Java implementation separates the **graph definition object** from the **execution runtime**. A two-stage structure where the builder creates an immutable graph definition and the runtime takes that definition and creates a run handle fits. Judging from Python's `graph_signature_hash` and .NET's restore compatibility gate, it is advantageous for checkpoint/resume that the graph definition has an independent identity. ([Python graph signature](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L330-L347), [.NET restore compatibility](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L404-L412))
- For the Java edge model it is recommended to keep the runtime edge kinds narrow as `DIRECT`, `FAN_OUT`, and `FAN_IN` as in `.NET`, and to handle a high-level switch/multi-selection DSL through builder lowering as in Python. This keeps the runtime state and observability simple. ([.NET EdgeKind](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Edge.cs#L11-L25), [.NET SwitchBuilder lowering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/SwitchBuilder.cs#L91-L96), [Python SwitchCaseEdgeGroup](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L806-L944))
- For the Java executor API it is better to compromise between the compile-time generator advantage of `.NET` and Python's simple annotation model and to put **annotation-processor-based route registration** on the preferred path. Cold start and validation quality become better than in a runtime reflection-only model. ([.NET Generator](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/ExecutorRouteGenerator.cs#L29-L75), [Generated source builder](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows.Generators/Generation/SourceBuilder.cs#L71-L247))
- Java must never restore a serialized edge callable automatically and must allow only **a symbolic name plus explicit registry rebinding** as in Python. It is safer for an unrestorable callable to raise an error fail-closed. ([Python missing callable](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L50-L72), [Python Edge.from_dict](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L219-L241))
- For the Java concurrency model a structure with a per-executor serialization lock as the default, as in Python, while allowing parallelism at the edge-runner level, is safe. This approach reduces multi-source same-target races while keeping the fan-out parallelism. ([Python executor lock](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_executor.py#L202-L244), [Python runner edge parallelism](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L201-L229))

## Concrete acceptance scenarios

1. **The build must fail when an unbound executor remains.** .NET tracks placeholder/unbound executors separately and rejects them in `Build()`, and a test pins this. ([.NET unbound validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L543-L551), [.NET test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L25-L36))

2. **The build must fail when there is an executor unreachable from the start executor.** .NET checks this with a BFS-style reachability walk, and a test pins the unreachable case. ([.NET reachability validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilder.cs#L553-L613), [.NET unreachable test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/WorkflowBuilderTests.cs#L39-L49))

3. **When the same agent instance is reused on several edges, the Python builder must reuse the same wrapper.** A test verifies that even when the same agent is used three times, the number of `AgentExecutor` wrappers is not duplicated. ([Python wrapper reuse logic](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L208-L223), [Python wrapper reuse test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L141-L157))

4. **When different agents converge on the same executor id, the Python build must fail.** ([Python duplicate id guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L216-L223), [Python duplicate id test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L159-L167))

5. **When a direct edge condition is false the message must be dropped, but the routing itself must be treated as processed normally.** Both .NET and Python distinguish a false condition as its own drop state. ([.NET direct edge false condition](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/DirectEdgeRunner.cs#L27-L34), [Python single edge false condition](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L124-L147))

6. **Fan-in must execute the sink only after every source has emitted a message at least once.** .NET implements this rule with the internal state of `FanInEdgeRunner` and Python with `_buffer`. ([.NET fan-in buffer/release](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/FanInEdgeRunner.cs#L34-L68), [Python fan-in readiness](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge_runner.py#L331-L401))

7. **An executor failure must emit an executor-level failure event first and then be promoted to a workflow-level failure.** The Python tests pin this order. ([Python executor_failed ordering test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_states.py#L31-L61), [Python second-executor failure ordering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_states.py#L89-L118))

8. **When an executor emits a reserved output/lifecycle event directly, the framework must reject it and replace it with a warning.** ([Python reserved-event guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L382-L401))

9. **When a serialized edge is restored without the original callable, that callable must be a fail-closed placeholder.** That is, the routing must not change silently. ([Python missing callable](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L50-L72), [SwitchCase placeholder case](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_edge.py#L696-L722))

10. **An explicit output designation must fail at build time when it is empty, duplicated, or overlapping.** The Python builder implements this contract explicitly. ([Python designation validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_builder.py#L686-L725))
