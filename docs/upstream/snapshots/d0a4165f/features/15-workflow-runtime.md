# 15-workflow-runtime

## 상태/스냅샷

- 이 문서는 **빌드된 워크플로를 실제로 실행하는 런타임 계층**만 다룬다. 대상은 .NET의 `Run`/`StreamingRun`/`AsyncRunHandle`/`InProcessRunner`/`InProcessRunnerContext`/`StateManager`와 Python의 `Workflow.run(...)`/`RunnerImpl`/`InProcRunnerContext`/`WorkflowContext`/`State`다. 그래프 정의, builder DSL, edge topology 자체는 별도 문서 범위다. ([.NET Run](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L13-L18), [.NET StreamingRun](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L13-L17), [.NET InProcessRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L17-L24), [Python Workflow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L208-L277), [Python RunnerImpl](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L45-L58), [Python InProcRunnerContext](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L315-L343))
- 런타임 스냅샷의 핵심 구성요소는 양쪽 모두 유사하다. 현재 입력 큐, pending external request registry, emitted event buffer/stream, shared state, 그리고 현재 run status가 따로 관리된다. .NET `Run`은 내부 `_eventSink`와 bookmark 기반 `NewEvents`를 가지며, `InProcessRunnerContext`는 `_queuedExternalDeliveries`, `_externalRequests`, `_nextStep`, `StateManager`를 들고 있다. Python은 `Workflow`가 `_status`와 `_active_run`을 들고, `InProcRunnerContext`가 `_messages`, `_event_queue`, `_pending_request_info_events`, runtime checkpoint storage override를 가진다. ([.NET Run event sink](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L19-L35), [.NET Run bookmarks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L52-L79), [.NET runner context fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L24-L40), [Python workflow runtime fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L362-L384), [Python runner context fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L324-L343))

## 목적·경계

### 목적

- 런타임 계층의 목적은 **(1) 입력을 받아 실행을 시작하고**, **(2) superstep/iteration 루프를 돌며 executor 간 메시지를 전달하고**, **(3) 외부 입력 요청·상태 변화·오류를 관찰 가능한 이벤트로 표면화하는 것**이다. .NET은 in-proc runner와 run handle이 이 역할을 맡고, Python은 `Workflow.run(...)`와 `RunnerImpl`이 같은 책임을 수행한다. ([.NET InProcessRunner responsibilities](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L17-L24), [.NET Run/StreamingRun API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L13-L18), [Python Workflow execution overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L211-L243), [Python RunnerImpl loop](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L106-L177))

### 경계

- 포함 범위는 다음과 같다.
  - run handle과 execution mode
  - run context와 external input/response correlation
  - workflow events와 status timeline
  - shared state commit 모델
  - streaming, cancellation, error propagation
- 제외 범위는 다음과 같다.
  - 그래프의 정적 정의와 validation 규칙
  - orchestration별 conversation 정책
  - declarative YAML lowering
  - hosting/web transport와 outer session store  
  이 분리는 코드 구조에서도 분명하다. `.NET`은 `InProc/*`, `Execution/*`, `Run.cs`, `StreamingRun.cs`, Python은 `_workflow.py`, `_runner.py`, `_runner_context.py`, `_workflow_context.py`, `_state.py`가 직접 대상이다. ([.NET runtime files](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L17-L24), [.NET state manager](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L13-L29), [Python workflow core files](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L208-L277), [Python state file](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L6-L18))

## 공개 API·타입

### .NET

- 비스트리밍 실행 핸들은 `Run`, 스트리밍 실행 핸들은 `StreamingRun`이다. 둘 다 `GetStatusAsync()`를 제공하고, `Run`은 `OutgoingEvents`, `NewEvents`, `ResumeAsync(...)`를, `StreamingRun`은 `WatchStreamAsync(...)`, `SendResponseAsync(...)`, `TrySendMessageAsync(...)`, `CancelRunAsync()`를 제공한다. ([Run API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L38-L128), [StreamingRun API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L26-L109))
- 상태 enum은 `RunStatus`이며 `NotStarted`, `Idle`, `PendingRequests`, `Ended`, `Running`을 가진다. ([RunStatus](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/RunStatus.cs#L8-L34))
- 관찰 가능한 이벤트 타입은 `WorkflowEvent` 파생형으로 정의되며, inspected public derived set에는 `ExecutorEvent`, `SuperStepEvent`, `WorkflowStartedEvent`, `WorkflowErrorEvent`, `WorkflowWarningEvent`, `WorkflowOutputEvent`, `RequestInfoEvent`, `MagenticOrchestratorEvent`가 포함된다. 즉 .NET은 상태를 event보다 handle polling으로 노출하는 경향이 강하다. ([WorkflowEvent derived types](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs#L11-L20), [Run.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [StreamingRun.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L31-L35))
- workflow context surface는 `IWorkflowContext`이고, bound implementation은 state read/write, output yield, message send, halt request를 노출한다. ([BoundWorkflowContext methods](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L347-L385))

([WorkflowEvent fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L146-L235), [WorkflowRunResult](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L103-L166))

## 상세 실행 흐름

### 1. Run 생성과 실행 모드 선택

- .NET `AsyncRunHandle` 생성자는 workflow runner와 checkpoint handle, execution mode를 받아 내부 event stream 구현을 고른다. `ExecutionMode.OffThread`는 `StreamingRunEventStream`, `ExecutionMode.Subworkflow`는 run loop 없는 `StreamingRunEventStream`, `ExecutionMode.Lockstep`은 `LockstepRunEventStream`을 선택한다. 생성 시 이미 pending message/request가 있으면 run loop를 깨운다. ([AsyncRunHandle mode selection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L24-L45))
- .NET top-level runner는 `BeginStreamAsync(...)`와 `ResumeStreamAsync(...)`로 handle을 만들고, `ResumeStreamAsync(...)`는 checkpoint restore 후 필요하면 pending request 재발행 플래그를 세운 뒤 새 handle을 반환한다. ([BeginStreamAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L160-L164), [ResumeStreamAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L166-L191))
- Python은 `Workflow.run(...)`이 먼저 parameter combination을 검증하고, active run이 있으면 동시 실행을 즉시 거부한다. 그 뒤 runtime checkpoint storage override를 정리하고, fresh run / responses-only / checkpoint restore / restore-then-send-responses 모드를 하나의 `ResponseStream`로 캡슐화한다. ([parameter validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L940-L985), [active-run guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L791), [execution mode resolution](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L966-L1010))

### 2. 입력 수락과 run context 초기 적재

- .NET `InProcessRunner.EnqueueMessageUntypedAsync(...)`는 run 종료 여부를 확인한 뒤 입력 타입이 start executor가 처리 가능한지 검사하고, 합격한 메시지를 runner context의 external delivery queue에 넣는다. `ExternalResponse`는 별도 경로로 처리된다. ([input validation and enqueue](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L97-L148))
- .NET `InProcessRunnerContext`는 external message와 external response를 `_queuedExternalDeliveries`에 함수 형태로 적재한다. superstep이 시작될 때 `AdvanceAsync()`가 이 큐를 순차적으로 비우는데, 주석상 edge state mutation 가능성 때문에 병렬 처리를 의도적으로 피한다. ([queue external message/response](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L129-L181), [AdvanceAsync sequential drain](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L193-L205))
- Python fresh run은 `_execute_with_message_or_checkpoint(...)`가 start executor id를 target으로 하는 internal `WorkflowMessage`를 만들어 runner context에 넣는다. `responses=...` 경로는 pending request registry를 조회해 response type을 강제한 뒤, original request metadata가 붙은 `WorkflowMessage(type=RESPONSE)`를 source executor로 보낸다. ([fresh message seeding](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L657-L680), [send responses internal](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1011-L1041), [runner context response message creation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L545-L575))

### 3. Superstep / Iteration 루프

- .NET in-proc runner는 `AdvanceAsync()`가 돌려준 `StepContext`에 메시지나 external deliveries나 joined subworkflow work가 있으면 실제 superstep을 수행한다. superstep은 step-start event, receiver별 메시지 전달, joined subworkflow runners 실행, checkpoint, step-complete event 순서로 진행된다. ([RunSuperStepAsync gate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L212-L240), [RunSuperstepAsync body](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L305-L336))
- .NET step start/complete event payload는 `InProcStepTracer`가 만든다. `Advance(...)`는 `SuperStepStartedEvent`와 sending executor set / external message 여부를, `Complete(...)`는 activated/instantiated executors, pending messages/requests, state updated 여부, checkpoint info를 포함한 `SuperStepCompletedEvent`를 만든다. ([InProcStepTracer.Advance](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcStepTracer.cs#L34-L62), [InProcStepTracer.Complete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcStepTracer.cs#L64-L70))
- Python `RunnerImpl.run_until_convergence()`는 pre-loop events를 먼저 drain하고, 각 iteration에서 `WorkflowEvent.superstep_started(...)`를 emit한 뒤 `_run_iteration()` task와 event polling을 병행한다. iteration이 끝나면 state를 commit하고 checkpoint를 만들고 `superstep_completed`를 emit하며, 더 이상 메시지가 없으면 converge한다. ([run_until_convergence](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L106-L177))
- Python `_run_iteration()`은 source executor별 drained message batch를 꺼내 edge runners로 병렬 전달한다. 같은 edge runner 내부에서는 메시지 순서를 유지한다. ([run_iteration and per-edge ordering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L179-L229))

### 4. 메시지, 이벤트, 상태 timeline

- .NET의 런타임 이벤트는 `RequestInfoEvent`, `WorkflowOutputEvent`, `WorkflowErrorEvent`, `Executor*Event`, `SuperStep*Event` 중심이다. 반면 상태는 first-class event보다 `Run.GetStatusAsync()` / `StreamingRun.GetStatusAsync()`로 읽는 handle state로 노출된다. ([WorkflowEvent derived set](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs#L11-L20), [Run.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [StreamingRun.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L31-L35))
- .NET `Run`은 stream을 내부 `_eventSink`에 모아 `OutgoingEvents`와 bookmark 기반 `NewEvents`로 돌려준다. 즉 data-plane event re-consumption과 incremental polling 둘 다 지원한다. ([Run event accumulation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L19-L35), [NewEvents bookmark](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L54-L79))
- Python은 반대로 status를 explicit event로 emit한다. `Workflow._run_workflow_with_tracing(...)`는 run 시작 시 `started`, 이어서 `status(IN_PROGRESS)`, 첫 pending request가 생기면 `status(IN_PROGRESS_PENDING_REQUESTS)`, 종료 시 `status(IDLE)` 또는 `status(IDLE_WITH_PENDING_REQUESTS)`, 실패 시 `failed`와 `status(FAILED)`를 낸다. ([status event emission](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L623))
- Python `WorkflowRunResult`는 data-plane events와 status timeline을 분리 저장한다. `get_outputs()`, `get_intermediate_outputs()`, `get_request_info_events()`, `get_final_state()`, `status_timeline()`이 제공된다. non-streaming finalizer는 기본적으로 `started`를 버리고 `status`는 별도 timeline에 넣으며, `include_status_events=True`일 때만 inline 포함시킨다. ## 상태·영속화

- .NET 런타임 문맥에서 영속화는 두 층으로 보인다. 첫째, 현재 run 안에서 `StateManager`가 staged updates와 live scopes를 관리한다. 둘째, restore 시 `InProcessRunnerContext.ImportStateAsync(...)`가 queued external deliveries를 비우고 `_nextStep` 메시지와 `_externalRequests`를 checkpoint 상태로 교체한다. 즉 restore는 “기존 in-memory timeline을 지우고 checkpoint timeline으로 교체”하는 의미다. ([clear buffered events before restore](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L187-L208))

([State export/import](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L106-L118), [build checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L421-L471), [apply checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L498-L515))

([state persists across runs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L245-L247), [fresh run resets iteration but not shared state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L534-L566))

## 동시성·스트리밍·취소

### 동시성

- .NET은 workflow-level concurrent reuse를 명시적 capability로 다룬다. concurrent runs가 활성화되면 workflow ownership 대신 ownership check만 수행하고, 그렇지 않으면 `TakeOwnership(...)`로 동일 workflow 인스턴스의 중복 사용을 금지한다. ([runner context ownership handling](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L41-L72), [workflow ownership rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Workflow.cs#L153-L201))
- Python은 동일 workflow 인스턴스의 concurrent runs를 허용하지 않는다. guard는 `_active_run` weakref이며, 이전 stream이 살아 있는 동안 새 `run()`은 `WorkflowException`으로 실패한다. ([active run field](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L367-L384), [concurrency rejection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L791))

### 스트리밍

- .NET `StreamingRun.WatchStreamAsync(...)`는 `blockOnPendingRequest=true`면 pending-request halt에서 일시정지 후 response가 오면 계속하고, `false`면 그 halt에서 stream을 끝낸다. consumer cancellation은 stream만 끝내고 workflow execution은 취소하지 않는다. ([WatchStreamAsync semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L66-L100))
- .NET background run loop는 `StreamingRunEventStream`이 맡는다. 이 루프는 첫 input을 기다렸다가, 실제 work가 생기면 `RunStatus.Running`으로 전환하고 `WorkflowStartedEvent`를 event channel에 쓰며, halt 시점엔 internal halt signal로 consumer를 깨운다. ([run loop wait/start/halt](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs#L80-L139), [consumer stream termination rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs#L213-L275))
- Python은 unified `ResponseStream`를 쓴다. caller가 `stream=True`로 받은 stream을 iterate하면 raw `WorkflowEvent`들이 그대로 흐르고, non-streaming이면 같은 stream의 finalizer가 `WorkflowRunResult`로 변환한다. ([run returns ResponseStream](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L779-L795), [finalizer](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L913-L938))

### 취소

- .NET은 public `CancelRunAsync()`를 제공한다. `AsyncRunHandle.CancelRunAsync()`는 `_endRunSource.Cancel()` 후 event stream stop을 await한다. `StreamingRun.CancelRunAsync()`는 이를 그대로 위임한다. ([AsyncRunHandle cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L165-L170), [StreamingRun cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L102-L107))
- Python core workflow surface에서는 inspected 범위상 public `cancel()` equivalent가 보이지 않았다. cancellation은 `RunnerImpl.run_until_convergence()` 내부에서 `asyncio.CancelledError`를 잡아 iteration task를 cancel하고 다시 전파하는 내부 처리로 나타난다. 또한 `WorkflowRunState.CANCELLED` enum은 존재하지만 inspected `Workflow.run()` 경로에서 이를 emit하는 코드는 보이지 않았다. ([RunnerImpl cancellation path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142), [WorkflowRunState includes CANCELLED](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L58-L67))

## 문서 차이

- Python 코드에는 `WorkflowRunState.CANCELLED` enum이 있으나, inspected `Workflow.run()` / `_run_workflow_with_tracing()` 경로에서는 `status(CANCELLED)`를 emit하는 코드가 보이지 않았다. 따라서 문서화 관점에서는 “cancelled 상태 개념은 정의돼 있지만, 현재 inspected public runtime path에서 실제 노출은 확인되지 않음”으로 기록하는 것이 코드 우선 해석이다. ([WorkflowRunState enum](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L58-L67), [run status emission path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L623))
- Python `Workflow.run()` 문서와 코드는 “shared state persists across run calls”를 매우 강하게 전제한다. 즉 fresh run도 state reset이 아니라 새로운 message를 같은 workflow instance에 추가하는 의미다. 이 점은 일반적인 stateless request/response mental model과 다를 수 있으므로 문서보다 코드를 우선해 이해해야 한다. ([state persists across runs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L245-L247), [fresh run semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L534-L566))
- .NET은 상태를 explicit status event보다 handle polling으로 노출하는 구조라, Python 쪽 status timeline 기반 분석 코드를 그대로 옮기면 맞지 않는다. 즉 런타임 관찰 API는 언어 간 표면이 다르다. ([.NET GetStatusAsync only](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [Python status_timeline](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L164-L166))

## Java 결정

- Java 런타임은 `.NET`처럼 **명시적 run handle 객체**를 두는 편이 낫다. Python의 unified `run(stream=...)`는 간단하지만, 운영 제어 관점에서는 `.NET`의 `GetStatusAsync()` / `sendResponse()` / `cancel()` 분리가 더 명확하다. 따라서 Java는 `WorkflowRunHandle` 하나에 streaming iterator, status, response submit, cancel을 모으고, non-streaming helper는 그 위에 얹는 구조를 권장한다. ([.NET Run/StreamingRun split](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L38-L128), [Python unified run](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L683-L795))
- Java는 **explicit status event stream도 같이 제공**하는 것이 좋다. .NET처럼 poll-only로 가면 상태 변화 추적용 audit/telemetry consumer가 복잡해지고, Python처럼 event-only로 가면 imperative control plane이 약해진다. 두 방식을 같이 제공하는 절충안이 적합하다. ([.NET polling status](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [Python explicit status events](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L598))
- Java shared state는 `.NET`의 scoped model을 기본으로 두되, Python처럼 committed/pending 2층 버퍼를 명시적으로 문서화해야 한다. 특히 superstep boundary commit semantics와 multi-writer conflict policy를 public contract로 적어야 한다. ([.NET scoped state access](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L364-L380), [Python state buffer model](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L6-L18))
- Java는 public `cancel()`를 반드시 제공해야 한다. inspected Python core처럼 internal cancellation만 있는 모델은 운영 환경에서 부족하다. ([.NET public cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L102-L107), [Python lack of public cancel in inspected path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142))
- Java는 pending request overlap에 대해 Python처럼 warning-only 허용보다, 기본은 **새 message 금지** 또는 **resume token required** 정책이 더 안전하다. 최소한 모드 선택 가능해야 한다. Python test가 보여주는 moved-on state 위험은 production에선 위험하다. ([Python overlap warning](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L847-L872), [Python overlap test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))

## 구체 acceptance scenarios

1. **비스트리밍 실행 완료**  
   단순 workflow를 non-streaming으로 실행하면 `.NET`은 `Run.GetStatusAsync()==Idle`, Python은 `WorkflowRunResult.get_final_state()==IDLE`이어야 한다. ([.NET non-streaming idle test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessExecutionTests.cs#L23-L48), [Python non-streaming idle test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L183-L199))

2. **스트리밍 실행 완료**  
   동일 workflow를 streaming으로 실행하면 caller는 run 도중 events를 받고, 종료 후 final status는 idle이어야 한다. ([.NET streaming idle test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessExecutionTests.cs#L50-L88), [Python streaming run test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L145-L163))

3. **pending request 상태 전이**  
   executor가 외부 입력을 요청하면 Python에서는 `IN_PROGRESS_PENDING_REQUESTS` 후 `IDLE_WITH_PENDING_REQUESTS` status timeline이 보여야 하고, .NET resumed handle은 `RunStatus.PendingRequests`를 반환해야 한다. ([Python pending request status test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_states.py#L137-L149), [.NET PendingRequests after resume](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L124-L138))

4. **executor failure ordering**  
   failing executor가 있으면 Python은 `executor_failed`가 `failed`보다 먼저 나와야 하며, framework origin이어야 한다. ([Python failure ordering test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_states.py#L31-L61))

5. **fresh message while pending request**  
   Python에서는 pending request가 남아 있을 때 fresh message run이 warning과 함께 허용되지만, 이후 old request response는 moved-on state에 적용될 수 있다. 이 위험이 test로 고정되어 있어야 한다. ([Python overlap test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))

6. **response port correlation 보호**  
   .NET에서는 response의 `PortId`가 origin request의 port와 다르면 예외를 던져야 한다. ([.NET correlation check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L162-L173))

7. **state persistence across executors**  
   .NET state는 checkpoint 유무와 관계없이 superstep 간 유지되어야 하며, validation executor가 writer executor가 쓴 값을 읽을 수 있어야 한다. ([.NET state persistence no checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessStateTests.cs#L81-L110), [.NET state persistence checkpointed](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessStateTests.cs#L112-L143))

8. **stream consumer cancellation과 workflow cancellation 분리**  
   .NET에서 `WatchStreamAsync(...)`에 준 cancellation token 취소는 stream만 끝내고 workflow 자체는 취소하지 않아야 하며, workflow cancel은 `CancelRunAsync()`로 별도 수행해야 한다. ([StreamingRun cancellation semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L72-L107))
