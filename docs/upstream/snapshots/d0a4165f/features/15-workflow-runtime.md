# 15-workflow-runtime

## State/snapshot

- This document covers only the **runtime layer that actually executes a built workflow**. The subjects are .NET's `Run`/`StreamingRun`/`AsyncRunHandle`/`InProcessRunner`/`InProcessRunnerContext`/`StateManager` and Python's `Workflow.run(...)`/`RunnerImpl`/`InProcRunnerContext`/`WorkflowContext`/`State`. The graph definition, the builder DSL, and the edge topology itself are the scope of a separate document. ([.NET Run](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L13-L18), [.NET StreamingRun](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L13-L17), [.NET InProcessRunner](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L17-L24), [Python Workflow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L208-L277), [Python RunnerImpl](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L45-L58), [Python InProcRunnerContext](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L315-L343))
- The core components of the runtime snapshot are similar on both sides. The current input queue, the pending external request registry, the emitted event buffer/stream, the shared state, and the current run status are managed separately. The .NET `Run` has an internal `_eventSink` and bookmark-based `NewEvents`, and `InProcessRunnerContext` holds `_queuedExternalDeliveries`, `_externalRequests`, `_nextStep`, and the `StateManager`. In Python the `Workflow` holds `_status` and `_active_run`, and `InProcRunnerContext` holds `_messages`, `_event_queue`, `_pending_request_info_events`, and the runtime checkpoint storage override. ([.NET Run event sink](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L19-L35), [.NET Run bookmarks](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L52-L79), [.NET runner context fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L24-L40), [Python workflow runtime fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L362-L384), [Python runner context fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L324-L343))

## Purpose and boundary

### Purpose

- The purpose of the runtime layer is **(1) to take the input and start execution**, **(2) to run the superstep/iteration loop and deliver messages between executors**, and **(3) to surface external input requests, state changes, and errors as observable events**. In .NET the in-proc runner and the run handle take that role, and in Python `Workflow.run(...)` and `RunnerImpl` carry the same responsibility. ([.NET InProcessRunner responsibilities](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L17-L24), [.NET Run/StreamingRun API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L13-L18), [Python Workflow execution overview](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L211-L243), [Python RunnerImpl loop](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L106-L177))

### Boundary

- The included scope is as follows.
  - the run handle and the execution mode
  - the run context and external input/response correlation
  - workflow events and the status timeline
  - the shared state commit model
  - streaming, cancellation, error propagation
- The excluded scope is as follows.
  - the static definition of the graph and the validation rules
  - the per-orchestration conversation policy
  - declarative YAML lowering
  - hosting/web transport and the outer session store  
  This separation is clear in the code structure as well. The direct subjects are `InProc/*`, `Execution/*`, `Run.cs`, and `StreamingRun.cs` in `.NET`, and `_workflow.py`, `_runner.py`, `_runner_context.py`, `_workflow_context.py`, and `_state.py` in Python. ([.NET runtime files](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L17-L24), [.NET state manager](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L13-L29), [Python workflow core files](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L208-L277), [Python state file](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L6-L18))

## Public APIs and types

### .NET

- The non-streaming execution handle is `Run` and the streaming execution handle is `StreamingRun`. Both provide `GetStatusAsync()`; `Run` provides `OutgoingEvents`, `NewEvents`, and `ResumeAsync(...)`, and `StreamingRun` provides `WatchStreamAsync(...)`, `SendResponseAsync(...)`, `TrySendMessageAsync(...)`, and `CancelRunAsync()`. - The state enum is `RunStatus`, with `NotStarted`, `Idle`, `PendingRequests`, `Ended`, and `Running`. ([RunStatus](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/RunStatus.cs#L8-L34))
- The observable event types are defined as `WorkflowEvent` derivatives, and the inspected public derived set includes `ExecutorEvent`, `SuperStepEvent`, `WorkflowStartedEvent`, `WorkflowErrorEvent`, `WorkflowWarningEvent`, `WorkflowOutputEvent`, `RequestInfoEvent`, and `MagenticOrchestratorEvent`. .NET therefore tends to expose state through handle polling rather than through events. ([WorkflowEvent derived types](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs#L11-L20), [Run.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [StreamingRun.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L31-L35))
- The workflow context surface is `IWorkflowContext`, and the bound implementation exposes state read/write, output yield, message send, and halt request. ([BoundWorkflowContext methods](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L347-L385))

It also combines `message`, `responses`, `checkpoint_id`, `checkpoint_storage`, and `include_status_events` in a single API. ([Workflow.run overloads](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L683-L751))
- The run state enum is `WorkflowRunState`, with `STARTED`, `IN_PROGRESS`, `IN_PROGRESS_PENDING_REQUESTS`, `IDLE`, `IDLE_WITH_PENDING_REQUESTS`, `FAILED`, and `CANCELLED`. ([WorkflowRunState](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L58-L67))
- The Python event carrier is the single generic `WorkflowEvent`, with fields such as `type`, `origin`, `state`, `details`, `executor_id`, `request_id`, and `iteration`. `WorkflowRunResult` stores the data-plane event list and the status timeline separately. ([WorkflowEvent fields](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L146-L235), [WorkflowRunResult](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L103-L166))
- The runtime context an executor receives is `WorkflowContext`. It provides `send_message()`, `yield_output()`, `add_event()`, `request_info()`, `get_state()`, `set_state()`, `is_streaming()`, and so on. ([WorkflowContext methods](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L318-L490))

## Detailed execution flow

### 1. Run creation and execution mode selection

- The .NET `AsyncRunHandle` constructor takes the workflow runner, the checkpoint handle, and the execution mode and picks the internal event stream implementation. `ExecutionMode.OffThread` picks `StreamingRunEventStream`, `ExecutionMode.Subworkflow` picks a `StreamingRunEventStream` without a run loop, and `ExecutionMode.Lockstep` picks `LockstepRunEventStream`. When there are already pending messages/requests at creation time it wakes the run loop. ([AsyncRunHandle mode selection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L24-L45))
- The .NET top-level runner creates handles with `BeginStreamAsync(...)` and `ResumeStreamAsync(...)`, and `ResumeStreamAsync(...)` returns a new handle after restoring the checkpoint and, when necessary, setting the pending request republish flag. ([BeginStreamAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L160-L164), [ResumeStreamAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L166-L191))
- In Python, `Workflow.run(...)` first validates the parameter combination and immediately refuses concurrent execution when there is an active run. It then sorts out the runtime checkpoint storage override and encapsulates the fresh run / responses-only / checkpoint restore / restore-then-send-responses modes into a single `ResponseStream`. ([parameter validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L940-L985), [active-run guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L791), [execution mode resolution](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L966-L1010))

### 2. Input acceptance and the initial loading of the run context

- The .NET `InProcessRunner.EnqueueMessageUntypedAsync(...)` checks whether the run has ended, then checks whether the start executor can handle the input type, and puts an accepted message into the runner context's external delivery queue. An `ExternalResponse` is handled on a separate path. ([input validation and enqueue](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L97-L148))
- The .NET `InProcessRunnerContext` loads external messages and external responses into `_queuedExternalDeliveries` in function form. When a superstep starts, `AdvanceAsync()` drains that queue sequentially, and the comment says parallel processing is deliberately avoided because of possible edge state mutation. ([queue external message/response](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L129-L181), [AdvanceAsync sequential drain](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L193-L205))
- A Python fresh run has `_execute_with_message_or_checkpoint(...)` create an internal `WorkflowMessage` targeting the start executor id and put it into the runner context. The `responses=...` path looks up the pending request registry, enforces the response type, and then sends a `WorkflowMessage(type=RESPONSE)` carrying the original request metadata to the source executor. ([fresh message seeding](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L657-L680), [send responses internal](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1011-L1041), [runner context response message creation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L545-L575))

### 3. The superstep / iteration loop

- The .NET in-proc runner performs an actual superstep when the `StepContext` returned by `AdvanceAsync()` has messages, external deliveries, or joined subworkflow work. A superstep proceeds in the order step-start event, per-receiver message delivery, joined subworkflow runner execution, checkpoint, and step-complete event. ([RunSuperStepAsync gate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L212-L240), [RunSuperstepAsync body](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L305-L336))
- The .NET step start/complete event payloads are built by `InProcStepTracer`. `Advance(...)` builds a `SuperStepStartedEvent` with the sending executor set / whether there was an external message, and `Complete(...)` builds a `SuperStepCompletedEvent` including the activated/instantiated executors, the pending messages/requests, whether the state was updated, and the checkpoint info. ([InProcStepTracer.Advance](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcStepTracer.cs#L34-L62), [InProcStepTracer.Complete](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcStepTracer.cs#L64-L70))
- The Python `RunnerImpl.run_until_convergence()` drains the pre-loop events first, emits `WorkflowEvent.superstep_started(...)` on each iteration, and then runs the `_run_iteration()` task alongside event polling. When the iteration ends it commits the state, creates a checkpoint, emits `superstep_completed`, and converges when there are no more messages. ([run_until_convergence](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L106-L177))
- The Python `_run_iteration()` takes the drained message batch per source executor and delivers it to the edge runners in parallel. Inside the same edge runner the message order is preserved. ([run_iteration and per-edge ordering](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L179-L229))

### 4. Messages, events, and the state timeline

- The .NET runtime events are centred on `RequestInfoEvent`, `WorkflowOutputEvent`, `WorkflowErrorEvent`, the `Executor*Event` family, and the `SuperStep*Event` family. State, by contrast, is exposed as handle state read through `Run.GetStatusAsync()` / `StreamingRun.GetStatusAsync()` rather than as a first-class event. ([WorkflowEvent derived set](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowEvent.cs#L11-L20), [Run.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [StreamingRun.GetStatusAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L31-L35))
- The .NET `Run` collects the stream into the internal `_eventSink` and returns it through `OutgoingEvents` and bookmark-based `NewEvents`. It therefore supports both data-plane event re-consumption and incremental polling. ([Run event accumulation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L19-L35), [NewEvents bookmark](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L54-L79))
- Python conversely emits status as explicit events. `Workflow._run_workflow_with_tracing(...)` emits `started` at run start, then `status(IN_PROGRESS)`, then `status(IN_PROGRESS_PENDING_REQUESTS)` when the first pending request appears, then `status(IDLE)` or `status(IDLE_WITH_PENDING_REQUESTS)` at the end, and `failed` plus `status(FAILED)` on failure. ([status event emission](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L623))
- The Python `WorkflowRunResult` stores the data-plane events and the status timeline separately. It provides `get_outputs()`, `get_intermediate_outputs()`, `get_request_info_events()`, `get_final_state()`, and `status_timeline()`. The non-streaming finalizer discards `started` by default and puts `status` into the separate timeline, including it inline only when `include_status_events=True`. ([WorkflowRunResult helpers](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L123-L166), [finalizer behavior](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L913-L938))

### 5. Shared state and the run context

- The .NET `BoundWorkflowContext` exposes the state read/write API on top of a per-executor scope. `ReadStateAsync<T>(key, scopeName)`, `ReadOrInitStateAsync<T>(...)`, `QueueStateUpdateAsync(...)`, and `QueueClearScopeAsync(...)` are all delegated to the internal `StateManager`. ([BoundWorkflowContext state methods](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L364-L380))
- The .NET `StateManager` stages writes through `_queuedUpdates`, and `PublishUpdatesAsync(...)` gathers them per scope and writes them to storage. While queued updates remain it refuses export/import. It also forbids a read into the `object` type and requires a `PortableValue`. ([queued update reads/writes](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L104-L188), [publish/export/import rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L201-L273))
- The Python `State` is split into the two layers `_committed` and `_pending`. `set()` writes only into pending, `get()` looks at pending first, and `commit()` pushes into committed at the superstep boundary. The comment states explicitly that when several executors write the same key in the same superstep, last write wins. ([State semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L6-L18), [State set/get/commit](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L30-L100))
- The Python `WorkflowContext` provides `get_state()` / `set_state()` over a flat key space. Unlike .NET, the executor id/scopeName is not exposed in the public API. ([Python WorkflowContext state API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L436-L465))

### 6. Message sending and trace context propagation

- The .NET `InProcessRunnerContext.SendMessageAsync(...)` builds a trace carrier from the OpenTelemetry activity and sends it downstream in the `traceContext` of the `MessageEnvelope`. A source executor cannot send a message that is not one of its protocol-declared send types. ([.NET send_message trace injection and type declaration](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L213-L239))
- The Python `WorkflowContext.send_message(...)` also builds the `WorkflowMessage` inside a producer span and injects the trace context and the source span ids when observability is on. ([Python send_message trace injection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L318-L348))

## State and persistence

- In the .NET runtime context, persistence appears in two layers. First, inside the current run the `StateManager` manages the staged updates and the live scopes. Second, on restore, `InProcessRunnerContext.ImportStateAsync(...)` drains the queued external deliveries and replaces the `_nextStep` messages and `_externalRequests` with the checkpoint state. A restore therefore means “erase the existing in-memory timeline and replace it with the checkpoint timeline”. ([state manager export/import](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L243-L273), [.NET import state into runner context](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L456-L487))
- The .NET `AsyncRunHandle.RestoreCheckpointAsync(...)` drains the event stream buffer first, before the restore. Thanks to that order, stale events that occurred after the checkpoint are not mixed in for the caller after the restore. ([clear buffered events before restore](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L187-L208))
- In the Python runtime context, persistence is implemented as the combination of `State.export_state()` / `import_state()` and `InProcRunnerContext.build_checkpoint()/apply_checkpoint()`. `apply_checkpoint()` initializes the event queue and, while restoring the stored messages and the pending request_info events, puts the pending requests back into the event queue. ([State export/import](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L106-L118), [build checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L421-L471), [apply checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L498-L515))
- Python states explicitly that the shared state of the same `Workflow` instance persists across runs. Even for a fresh message run, the shared state is therefore not reset automatically, and only the iteration counter and the run kwargs are reset for the fresh turn. ([state persists across runs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L245-L247), [fresh run resets iteration but not shared state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L534-L566))

## Concurrency, streaming, and cancellation

### Concurrency

- .NET treats workflow-level concurrent reuse as an explicit capability. When concurrent runs are enabled it performs only an ownership check instead of taking workflow ownership, and otherwise it forbids duplicate use of the same workflow instance with `TakeOwnership(...)`. ([runner context ownership handling](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L41-L72), [workflow ownership rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Workflow.cs#L153-L201))
- Python does not allow concurrent runs of the same workflow instance. The guard is the `_active_run` weakref, and while a previous stream is alive a new `run()` fails with a `WorkflowException`. ([active run field](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L367-L384), [concurrency rejection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L791))

### Streaming

- The .NET `StreamingRun.WatchStreamAsync(...)` pauses at a pending-request halt when `blockOnPendingRequest=true` and continues once a response arrives, and ends the stream at that halt when it is `false`. Consumer cancellation only ends the stream and does not cancel the workflow execution. ([WatchStreamAsync semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L66-L100))
- The .NET background run loop is handled by `StreamingRunEventStream`. That loop waits for the first input, switches to `RunStatus.Running` once actual work appears, writes a `WorkflowStartedEvent` into the event channel, and wakes the consumer with an internal halt signal at a halt point. ([run loop wait/start/halt](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs#L80-L139), [consumer stream termination rules](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs#L213-L275))
- Python uses the unified `ResponseStream`. When the caller iterates the stream received with `stream=True`, raw `WorkflowEvent` objects flow through as they are, and when non-streaming the finalizer of the same stream converts it into a `WorkflowRunResult`. ([run returns ResponseStream](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L779-L795), [finalizer](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L913-L938))

### Cancellation

- .NET provides a public `CancelRunAsync()`. `AsyncRunHandle.CancelRunAsync()` calls `_endRunSource.Cancel()` and then awaits the event stream stop. `StreamingRun.CancelRunAsync()` delegates straight to it. ([AsyncRunHandle cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L165-L170), [StreamingRun cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L102-L107))
- On the Python core workflow surface no public `cancel()` equivalent was visible within the inspected scope. Cancellation appears as internal handling inside `RunnerImpl.run_until_convergence()`, which catches `asyncio.CancelledError`, cancels the iteration task, and re-propagates it. The `WorkflowRunState.CANCELLED` enum also exists, but no code emitting it was visible on the inspected `Workflow.run()` path. ([RunnerImpl cancellation path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142), [WorkflowRunState includes CANCELLED](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L58-L67))

## Errors, validation, and security

- A .NET executor failure can surface both as an `ExecutorFailedEvent` and as a `WorkflowErrorEvent`. The inspected in-proc runner catches a superstep execution exception and enqueues a `WorkflowErrorEvent`. `StreamingRunEventStream` also pushes a run loop exception into the event channel as a `WorkflowErrorEvent`. ([InProcessRunner catches workflow error](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L226-L235), [StreamingRunEventStream error publication](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs#L146-L169))
- .NET external response routing has a security check. `AddExternalResponseAsync(...)` checks whether the pending request exists and throws when the response's `PortInfo.PortId` differs from the port of the original request, blocking a forged response from entering a different port execution path. ([response port correlation check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L157-L173))
- The .NET state layer forbids an `object` read for serialization stability and requires a `PortableValue`. While queued updates remain, export/import is forbidden as well. ([state object-read guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L104-L110), [state export/import guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StateManager.cs#L243-L258))
- Python surfaces an executor failure as structured `WorkflowErrorDetails`. When an exception occurs, `Workflow._run_workflow_with_tracing(...)` drains the pending events first, then emits a `failed(details)` event and `status(FAILED)`, and re-raises the exception. ([WorkflowErrorDetails](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L70-L99), [failure emission path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L601-L623))
- Python does not provide in-process recovery from a mid-run failure. When in-flight executor messages still remain during a fresh `message` run it refuses the new run, and states that checkpointing must be used for recovery. ([no in-process recovery without checkpointing](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L827-L845))
- Python allows starting a fresh message or a checkpoint restore while pending requests remain, but leaves a warning. A fresh message does not abandon the old request, but because the executor/shared state moves forward, the code and the tests together state the risk that a later response can be applied to a moved-on workflow. ([warning on pending requests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L847-L872), [fresh message while pending test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))
- The Python `WorkflowContext.add_event()` replaces the event with a warning event when an executor tries to emit a reserved lifecycle/output event type directly. This is a security/validation device that protects the integrity of the runtime event channel. ([reserved event guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L382-L401))

### Summary of the .NET/Python differences

- **API shape**: .NET is split into `Run`/`StreamingRun`, and Python has the single `Workflow.run(...)` API. ([.NET Run/StreamingRun](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L13-L18), [Python run overloads](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L683-L751))
- **How state is exposed**: .NET is centred on `GetStatusAsync()` polling, and Python on explicit `status` events plus `WorkflowRunResult.status_timeline()`. ([.NET RunStatus API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [Python status events](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L598), [Python status_timeline](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L164-L166))
- **shared state shape**: .NET has scoped state based on the executor id plus an optional scope name, and Python has flat key-based shared state. ([.NET scoped state methods](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L364-L380), [Python get_state/set_state](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L436-L465))
- **Concurrent execution policy**: .NET allows concurrent shared execution when the capability matches, and Python forbids concurrent runs of the same instance. ([.NET concurrent gate](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L45-L52), [Python active run guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L757-L771))
- **Cancellation**: .NET has a public `CancelRunAsync()`, but no public cancel surface at the same level was visible on the inspected Python core path. ([.NET cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L102-L107), [Python runner cancellation only](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142))
- **pending request overlap semantics**: .NET continues around explicit resume handle/response APIs, while Python allows a fresh message and pending requests to coexist with a warning. ## Documentation differences

- The Python code has a `WorkflowRunState.CANCELLED` enum, but no code emitting `status(CANCELLED)` was visible on the inspected `Workflow.run()` / `_run_workflow_with_tracing()` path. From a documentation standpoint the code-first reading is therefore to record it as “the cancelled state concept is defined, but its actual exposure on the inspected public runtime path was not confirmed”. ([WorkflowRunState enum](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_events.py#L58-L67), [run status emission path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L623))
- The Python `Workflow.run()` documentation and code very strongly presume that “shared state persists across run calls”. A fresh run therefore means adding a new message to the same workflow instance rather than resetting the state. Because this can differ from the usual stateless request/response mental model, it has to be understood code first rather than documentation first. ([state persists across runs](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L245-L247), [fresh run semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L534-L566))
- Because .NET is structured to expose state through handle polling rather than explicit status events, porting Python-side status timeline based analysis code over as is does not fit. The runtime observation APIs therefore have different surfaces across the languages. ([.NET GetStatusAsync only](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [Python status_timeline](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L164-L166))

## Java decisions

- The Java runtime is better off having an **explicit run handle object** as in `.NET`. Python's unified `run(stream=...)` is simple, but from an operational control standpoint `.NET`'s separation of `GetStatusAsync()` / `sendResponse()` / `cancel()` is clearer. It is therefore recommended that Java gather the streaming iterator, status, response submit, and cancel into a single `WorkflowRunHandle` and put the non-streaming helper on top of it. ([.NET Run/StreamingRun split](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L38-L128), [Python unified run](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L683-L795))
- Java is better off **also providing an explicit status event stream**. Going poll-only as in .NET complicates audit/telemetry consumers that track state changes, and going event-only as in Python weakens the imperative control plane. A compromise that provides both is appropriate. ([.NET polling status](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Run.cs#L44-L47), [Python explicit status events](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L523-L598))
- Java shared state should take `.NET`'s scoped model as the base, but the two-layer committed/pending buffer must be documented explicitly as in Python. The superstep boundary commit semantics and the multi-writer conflict policy in particular must be written down as a public contract. ([.NET scoped state access](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L364-L380), [Python state buffer model](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_state.py#L6-L18))
- Java must provide a public `cancel()`. A model with only internal cancellation, like the inspected Python core, is insufficient in an operational environment. ([.NET public cancel](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L102-L107), [Python lack of public cancel in inspected path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner.py#L125-L142))
- For pending request overlap, a policy of **forbidding a new message** by default or of **requiring a resume token** is safer for Java than Python's warning-only allowance. At the very least the mode must be selectable. The moved-on state risk the Python test shows is dangerous in production. ([Python overlap warning](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L847-L872), [Python overlap test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))

## Concrete acceptance scenarios

1. **Non-streaming execution completion**  
   Running a simple workflow non-streaming must give `Run.GetStatusAsync()==Idle` in `.NET` and `WorkflowRunResult.get_final_state()==IDLE` in Python. ([.NET non-streaming idle test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessExecutionTests.cs#L23-L48), [Python non-streaming idle test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L183-L199))

2. **Streaming execution completion**  
   Running the same workflow streaming must let the caller receive events during the run, and the final status after the end must be idle. ([.NET streaming idle test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessExecutionTests.cs#L50-L88), [Python streaming run test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L145-L163))

3. **Pending request state transition**  
   When an executor requests external input, Python must show an `IN_PROGRESS_PENDING_REQUESTS` and then an `IDLE_WITH_PENDING_REQUESTS` status timeline, and the .NET resumed handle must return `RunStatus.PendingRequests`. ([Python pending request status test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_states.py#L137-L149), [.NET PendingRequests after resume](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L124-L138))

4. **Executor failure ordering**  
   When there is a failing executor, Python must emit `executor_failed` before `failed`, and it must be framework origin. ([Python failure ordering test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow_states.py#L31-L61))

5. **Fresh message while pending request**  
   In Python a fresh message run is allowed with a warning while a pending request remains, but a later response to the old request can then be applied to moved-on state. This risk must be pinned by a test. ([Python overlap test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))

6. **Response port correlation protection**  
   In .NET, when the response's `PortId` differs from the port of the origin request it must throw. ([.NET correlation check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L162-L173))

7. **State persistence across executors**  
   .NET state must be maintained across supersteps regardless of checkpointing, and a validation executor must be able to read the value a writer executor wrote. ([.NET state persistence no checkpoint](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessStateTests.cs#L81-L110), [.NET state persistence checkpointed](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/InProcessStateTests.cs#L112-L143))

8. **Separation of stream consumer cancellation and workflow cancellation**  
   In .NET, cancelling the cancellation token given to `WatchStreamAsync(...)` must only end the stream and must not cancel the workflow itself, and a workflow cancel must be performed separately with `CancelRunAsync()`. ([StreamingRun cancellation semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L72-L107))
