## Purpose and boundary

### Purpose

- This feature has three purposes.
  1. **Safely save and restore a workflow during execution.**
  2. **Pause execution at the point where an external response is required and then resume.**
  3. **Model human-in-the-loop patterns such as approval, human feedback, and external domain validation using a consistent request-response contract.**  
  In .NET, the request port and checkpoint manager take on this responsibility; in Python, `request_info()`, `WorkflowCheckpoint`, and the orchestration/declarative approval executors share the same responsibility. ([.NET AddExternalCall helper](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilderExtensions.cs#L169-L191), [.NET RequestInfoExecutor purpose](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/RequestInfoExecutor.cs#L15-L31), [Python request_info context API](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L403-L435), [Python declarative tool approval purpose](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_tools.py#L50-L83))

### Boundary

- The included scope is as follows.
  - checkpoint object/store/manager
  - checkpoint creation, latest lookup, and restore
  - reissuing of pending requests
  - request-response correlation
  - tool approval, agent approval, external loop
  - the HITL path of declarative `Question`/`RequestExternalInput`/`InvokeAzureAgent`/`InvokeFunctionTool`/`InvokeMcpTool`
- The excluded scope is as follows.
  - general superstep scheduling
  - static graph/edge definition
  - the general conversation policy of orchestration
  - outer hosting/session-store protocol  
  The code structure also reflects this separation. For `.NET`, the scope covers `Checkpoint*`, `Request*`, `AIContentExternalHandler`, and declarative object-model executors; for Python, the direct targets are `_checkpoint.py`, `_runner_context.py`, `_workflow.py`, the orchestration `_orchestration_request_info.py`, and the declarative `_executors_agents.py`/`_executors_tools.py`/`_executors_http.py`. ([.NET checkpoint files](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/CheckpointManager.cs#L11-L86), [.NET request/approval files](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/AIContentExternalHandler.cs#L14-L103), [Python checkpoint core](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_checkpoint.py#L30-L188), [Python orchestration approval](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_orchestration_request_info.py#L44-L242), [Python declarative agent/tool HITL](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_agents.py#L259-L352), [Python declarative tool approval](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_tools.py#L424-L559))

## Detailed execution flows

### 1. .NET checkpoint creation and restore

- .NET `InProcessRunner.CheckpointAsync(...)` first calls executor checkpoint hooks when a checkpoint manager is present, caches the workflow definition snapshot, then collects `RunnerStateData`, `stateData`, and `edgeData` through edge state export and state publish to create an internal `Checkpoint`. This checkpoint is linked to the last checkpoint as its parent. ([CheckpointAsync flow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L341-L369), [Checkpoint payload shape](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/Checkpoint.cs#L10-L40))
- Restore is handled by `RestoreCheckpointCoreAsync(...)`. This path checks workflow compatibility after the checkpoint lookup, then performs `StateManager.ImportStateAsync(...)`, `RunContext.ImportStateAsync(...)`, executor restore hooks, and edge-state import, and repopulates the checkpoint index. ([restore core flow](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L395-L438))
- For restore on a live run, `AsyncRunHandle.RestoreCheckpointAsync(...)` first drains the event buffer and then calls the checkpointing handle restore, and after restore it wakes up the run loop. The streaming resume start path has `ResumeStreamAsync(...)` perform the restore first, and then sets the `_needsRepublish` flag so that pending requests are re-emitted after the event stream is subscribed. ([clear-buffer-then-restore](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/AsyncRunHandle.cs#L187-L208), [resume stream with republish flag](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L166-L191), [republish consumption](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L198-L206))
- The checkpoint manager's determination of the “latest checkpoint” relies on the store index ordering contract. `ICheckpointStore.RetrieveIndexAsync(...)` must guarantee oldest-first, newest-last order, and `CheckpointManager.GetLatestCheckpointAsync(...)` treats the last element as the latest. ([index ordering contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/ICheckpointStore.cs#L14-L30), [GetLatestCheckpointAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/CheckpointManager.cs#L63-L86))

### 2. .NET request-response core flow

- The .NET core request-response revolves around `RequestPort<TRequest,TResponse>` and `ExternalRequest`/`ExternalResponse`. The builder helper `AddExternalCall<TRequest,TResponse>(...)` adds bidirectional edges between the source and the port to create the external call/response path. ([RequestPort](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/RequestPort.cs#L13-L33), [AddExternalCall](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/WorkflowBuilderExtensions.cs#L169-L191))
- `RequestInfoExecutor` handles three kinds of input.
  1. raw request payload  
  2. wrapped `ExternalRequest`  
  3. wrapped `ExternalResponse`  
  Upon receiving a request, it emits it externally via `RequestSink.PostAsync(request)`, and for a wrapped request it stores the original request in `_wrappedRequests` so that a later response can be rewrapped. ([RequestInfoExecutor routes](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/RequestInfoExecutor.cs#L38-L60), [HandleCatchAll/HandleAsync request paths](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/RequestInfoExecutor.cs#L65-L119))
- When a response arrives, `HandleAsync(ExternalResponse)` validates port compatibility and response type. If the original request is remembered as a wrapped request, it rewraps it into the form of the original request and sends it back to the workflow; otherwise it sends both the wrapped response and the unwrapped response payload to the workflow. Additionally, `_wrappedRequests` is subject to checkpoint save/restore. ([response handling and rewrap](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/RequestInfoExecutor.cs#L121-L170))
- At the runner context level, the pending request registry is `_externalRequests`. When preparing to enqueue a response, it first checks whether the request id exists, and throws an exception if `response.PortInfo.PortId` differs from the port id of the original request. Only upon successful validation does it consume the pending request. ([pending request registry and response validation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunnerContext.cs#L147-L181))
- This forged-port defense is fixed by a dedicated test. A forged response that reuses the same `RequestId` but carries a different `PortId` is rejected, and the legitimate response can still be completed normally afterward. ([forged port id rejection test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/ExternalResponsePortCorrelationTests.cs#L18-L59), [legitimate response after rejection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/ExternalResponsePortCorrelationTests.cs#L61-L104))

### 3. .NET pending request reissuing and approval persistence

- Pending requests restored from a checkpoint must be re-emitted as `RequestInfoEvent` after the run loop subscribes. To achieve this, `InProcessRunner.ResumeStreamAsync(...)` sets `_needsRepublish` and calls `RepublishPendingEventsAsync(...)` immediately after `StreamingRunEventStream` starts. ([resume with republish flag](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L169-L188), [RepublishPendingEventsAsync contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/InProc/InProcessRunner.cs#L198-L206), [stream startup republish](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Execution/StreamingRunEventStream.cs#L61-L67))
- This contract is fixed by `CheckpointResumeTests`. Pending request reissuing after resume, resumed status=`PendingRequests`, and completion without duplicates after a response are each verified. ([republish test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L20-L85), [resumed status test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L87-L138), [no duplicate after response](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L140-L230))
- Pending request persistence for the agent approval/function-call approval side is handled by `AIContentExternalHandler<TRequestContent,TResponseContent>`. This handler holds `_pendingRequests` as a concurrent dictionary, and treats reissuing as an idempotent no-op if the same request id is already pending. Checkpoint save/restore stores and restores a copy of the dictionary to the `MakeKey(id)_PendingRequests` state entry. ### 6. Python core request-response flow

- A Python executor can call `WorkflowContext.request_info(request_data, response_type, request_id=None)` to wait for an external response. This method only warns whether the executor has a corresponding `@response_handler`, and the actual request is created as a `WorkflowEvent.request_info(...)` and placed into the runner context pending map. ([request_info implementation](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow_context.py#L403-L435))
- `InProcRunnerContext.add_request_info_event(...)` accepts only `type='request_info'` events, stores them in `_pending_request_info_events`, and also puts them into the event queue. When a response arrives, `send_request_info_response(...)` removes the original event from the pending map, validates the request type/response type, and sends a `WorkflowMessage(type=RESPONSE)` carrying the original request metadata back to the source executor. ([pending request registry](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L534-L543), [response correlation and type check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_runner_context.py#L545-L575))
- `Workflow.run(responses=...)` queries the pending request map, rejects unknown request ids, coerces the response to the expected type, and then calls `send_request_info_response(...)` in parallel for each pending request. It then creates a response-entry checkpoint to make the “responses in-flight” state replayable. ([send responses internal](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L1011-L1041))
- Python allows a fresh message while pending requests remain. However, both code and tests explicitly state with a warning that this is dangerous behavior in which an old response can be applied to a moved-on state. ([warning on overlap](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L847-L872), [overlap test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))

## Concurrency, streaming, and cancellation

- In the .NET streaming run, using `WatchStreamAsync(blockOnPendingRequest: false)` returns control to the caller at the point where a pending request arises. This mode is appropriate for checkpoint/resume and HITL turn loops. While a request is pending, the caller can send a response via `SendResponseAsync(...)` to let the run loop proceed again. ([blockOnPendingRequest semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L80-L100), [SendResponseAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L38-L45))
- .NET pending approval re-emission is handled as idempotent. Even if the same request id reappears after checkpoint restore, `AIContentExternalHandler` does not perform a duplicate repost. This prevents a race in which the same pending request is created multiple times. ([idempotent pending request re-emission](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Specialized/AIContentExternalHandler.cs#L59-L71))
- Python can process the `responses + checkpoint_id` combination in a single `run(...)`, and in this case the request_info events that would be re-emitted during restore for which the caller has already provided a response are not shown again in the stream. In other words, duplicate event exposure on the restore-then-send response path is prevented. ([restore+responses path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L974-L1010), [skip already-handled request_info events](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L883-L891))
- The concurrency safety of the Python declarative approval flow is fixed by tests. Even when two approval requests for the same executor are pending, each response is bound to its own `original_request` payload and is not swapped. ([concurrent approvals do not swap](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L186-L205))
- On the cancellation side, `.NET` provides a public cancel surface, but within the scope of this document the checkpoint/HITL flow itself centers on resume/response rather than cancel. The Python core inspected path emphasizes request/response continuation and checkpoint replay more strongly than public cancel. ([.NET cancel surface](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/StreamingRun.cs#L102-L107), [Python run continuation semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L723-L739))

## Errors, validation, and security

- The .NET checkpoint store requires `RetrieveIndexAsync(...)` ordering as a contract. An unordered store causes “wrong latest checkpoint” resume, making it an incorrect implementation. ([ordering contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/ICheckpointStore.cs#L21-L30))
- The .NET file-system checkpoint store escapes filenames and simultaneously verifies index membership and file existence on lookup. ([escaped checkpoint filenames](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/FileSystemJsonCheckpointStore.cs#L131-L138), [retrieve checkpoint existence check](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/FileSystemJsonCheckpointStore.cs#L201-L216))

## Java decisions

- It is advisable for Java to place checkpoint and HITL on the **same continuation contract**. That is, “pending external requests + in-flight responses + shared state + executor snapshots” are all placed together in a single checkpoint object, and pending requests are re-emitted after restore. Both .NET and Python adopt this model. ([.NET checkpoint payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/Checkpoint.cs#L10-L40), [Python WorkflowCheckpoint payload](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_checkpoint.py#L30-L99))
- Rather than a Python-style warning-only overlap, Java is recommended to **prohibit fresh messages by default when pending requests remain**. Providing an opt-in override only when necessary is safer. As Python tests demonstrate, overlap carries the risk of an old response being applied to a moved-on state. ([Python overlap warning code](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L847-L872), [Python overlap behavior test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/tests/workflow/test_workflow.py#L113-L143))
- Java approval flow must default to the **original request payload immutable contract**. The Python declarative contract of treating `original_request` as the sole basis rather than re-reading side-channel state on resume is safer and more robust for concurrency. ([Python original_request contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L7-L21), [concurrent approvals do not swap](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L186-L205))
- Java file-based checkpoint storage must have path traversal validation and an allowed-type whitelist built in by default, as in Python. Simple JSON/Java serialization alone is unsafe. ([Python file path guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_checkpoint.py#L292-L310), [Python restricted decode](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_checkpoint.py#L362-L369))
- It is advisable for Java to provide first-class APIs such as `resumeFrom(checkpointId)`, `respond(requestId, payload)`, `listPendingRequests()`, and `latestCheckpoint()` on the run handle. A balance between the handle-oriented API of .NET and the unified API of Python is desirable, with operational control concentrated on the handle. ([.NET CheckpointableRunBase](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/CheckpointableRunBase.cs#L23-L48), [Python unified run params](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_workflow.py#L721-L740))

## Concrete acceptance scenarios

1. **Latest checkpoint lookup follows commit order.**  
   If the store guarantees oldest-first/newest-last order, `GetLatestCheckpointAsync()` returns the last element as the latest. ([ICheckpointStore ordering contract](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/Checkpointing/ICheckpointStore.cs#L21-L30), [GetLatestCheckpointAsync](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/src/Microsoft.Agents.AI.Workflows/CheckpointManager.cs#L73-L86))

2. **Resuming from a checkpoint with pending requests must re-surface request_info.**  
   In .NET, after resuming with a fresh handle, `RequestInfoEvent` must be re-emitted, and a test fixes this. ([republish pending requests test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L20-L85))

3. **The state immediately after resume must reflect pending requests.**  
   The `RunStatus` of a .NET resumed handle must be `PendingRequests`. ([resumed status test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/CheckpointResumeTests.cs#L87-L138))

4. **A forged response must be rejected even if the request id matches, when the port id differs.**  
   After rejection, the legitimate responder must still be able to complete normally. ([forged response rejection](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/ExternalResponsePortCorrelationTests.cs#L34-L59), [legitimate response still works](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/dotnet/tests/Microsoft.Agents.AI.Workflows.UnitTests/ExternalResponsePortCorrelationTests.cs#L61-L84))

5. **Tool approval deny must not execute the tool invocation.**  
   If a Python declarative approval response has `approved=False`, only a rejection result is stored in state and execution must proceed with `ActionComplete`. ([tool denial path](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_tools.py#L526-L546))

6. **Tool approval resume must use the original_request payload as the source-of-truth.**  
   Even if stale old state exists, the payload must prevail, and concurrent approvals must not be swapped. ([approval payload test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L170-L184), [concurrent approval test](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L186-L205), [stale state poison ignored](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/tests/test_declarative_approval_binding.py#L207-L220))

7. **In agent approval, an empty follow-up must be interpreted as approve and a non-empty follow-up as iterate.**  
   The orchestration `AgentRequestInfoExecutor` yields the original response on an empty message list and sends a new agent request when the message list is non-empty. ([approval vs iterate semantics](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/agent_framework_orchestrations/_orchestration_request_info.py#L103-L117), [tests](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/orchestrations/tests/test_orchestration_request_info.py#L131-L179))

8. **The declarative external loop must terminate cleanly when user input or an agent response causes the loop condition to become false.**  
   On termination, the external loop state must be cleared and `ActionComplete` sent to proceed to the next action. ([loop exit before invoke](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_agents.py#L921-L936), [loop exit after agent response](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/declarative/agent_framework_declarative/_workflows/_executors_agents.py#L973-L992))

9. **A checkpoint file path must not escape outside the storage root.**  
   Python file storage must reject a malicious checkpoint id via path validation. ([path traversal guard](https://github.com/microsoft/agent-framework/blob/d0a4165f170193ba1d026a259af40d35bb7eaefe/python/packages/core/agent_framework/_workflows/_checkpoint.py#L292-L310))
